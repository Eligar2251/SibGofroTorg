# 🚑 Админка не работает: инструкция по восстановлению

Ситуация, для которой написана эта инструкция: **сайт открывается, а админка — нет**
(«500» на `/api/admin/*`, «An error occurred in the Server Components render»,
пустые таблицы, «Неверный логин или пароль» при верном пароле).

Порядок действий — сверху вниз. Первые два шага отвечают на вопрос «что именно
сломалось», дальше — что нажать.

---

## Шаг 0. Узнать причину (30 секунд)

Откройте в браузере:

```
https://sibgofrotorg.ru/api/health/db?deep=1
```

Это страница диагностики (не требует входа). Найдите в ответе поле `"status"` и
`"hint"` — там уже написана причина и что делать. Расшифровка:

| `status` | Что случилось | Куда смотреть |
|---|---|---|
| `ok` | База в порядке — дело не в подключении | Шаг 5 (сессия/аккаунт) |
| `missing_env` | В приложении пропали переменные окружения | Шаг 4 |
| `bad_url` | Испорчен `SUPABASE_URL` | Шаг 4 |
| `invalid_key` | Supabase не принимает ключ (ротировали JWT-секрет, отключили legacy-ключи, вставили публичный ключ) | Шаг 2 |
| `project_paused` | Проект Supabase на паузе / ограничен тарифом | Шаг 1 |
| `project_missing` | Проекта по этому адресу больше нет | Шаг 3 |
| `network` / `timeout` | Контейнер не может достучаться до Supabase по сети | Шаг 3 |
| `schema` | Нет нужной таблицы — не применена SQL-миграция | Шаг 6 |

Тот же диагноз в терминале (если есть доступ к консоли):

```bash
node scripts/doctor.mjs
```

А внутри админки (когда она уже открывается) есть раздел
**Диагностика** — меню → «Диагностика» или адрес
`https://sibgofrotorg.ru/<ваш-путь-админки>/diagnostics`.

---

## Шаг 1. Проект Supabase на паузе

Бесплатные проекты Supabase приостанавливают за неактивность и при превышении
лимитов. Признак: `status=project_paused`, HTTP 404/503 с текстом про paused.

1. Откройте <https://supabase.com/dashboard> и войдите в аккаунт проекта.
2. Выберите проект. Если он на паузе — рядом будет кнопка **Restore project** /
   **Resume project**. Нажмите её и дождитесь статуса **Active** (1–2 минуты).
3. Обновите страницу `/api/health/db` — должно стать `status: ok`.
4. Админка заработает сама, переменные менять не надо.

Если проект приостанавливается постоянно — проверьте тариф и лимиты
(Settings → Usage): чаще всего это размер базы, трафик или число запросов.

## Шаг 2. Supabase не принимает ключ (`invalid_key`)

Так бывает в трёх случаях:

* в проекте нажали **Rotate JWT secret** — старые ключи (в том числе
  `service_role`) сразу перестают работать;
* в проекте **отключили legacy-ключи** (Supabase перешёл на новые ключи
  `sb_secret_…` / `sb_publishable_…`);
* в переменную случайно вставили **публичный** ключ вместо секретного.

Лечение одно — взять актуальные ключи и вставить их в переменные окружения.

### 2.1. Взять новые ключи

1. <https://supabase.com/dashboard> → ваш проект.
2. **Project Settings → API Keys**
   (в старом интерфейсе — **Settings → API**).
3. Скопируйте:
   * **Secret key** (он же `service_role` / `service_role key`) → это
     `SUPABASE_SERVICE_ROLE_KEY`. Ключ показывается один раз — сохраните его.
   * **Publishable key** (он же `anon public`) → это
     `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
4. **Project Settings → Data API** (старое — **Settings → API**) → скопируйте
   **Project URL** → это `SUPABASE_URL`. Вид: `https://xxxxxxxx.supabase.co`.

### 2.2. Вставить ключи в Timeweb Cloud

1. Панель Timeweb Cloud → **Приложения** → ваше приложение.
2. Раздел **Переменные окружения** (Environment variables).
3. Замените значения `SUPABASE_SERVICE_ROLE_KEY` и
   `NEXT_PUBLIC_SUPABASE_ANON_KEY` на новые (см. блок в шаге 4).
4. Сохраните и нажмите **Перезапустить** (если меняли `NEXT_PUBLIC_…` —
   именно **Пересобрать и запустить**, см. примечание в шаге 4).
5. Проверьте `/api/health/db` → должно быть `status: ok`.

> ⚠️ Ключ `service_role` даёт полный доступ к базе. Его нельзя вставлять в
> браузерный код, отправлять в чат, публиковать в GitHub. Если ключ «засветился» —
> сделайте Rotate и обновите переменную.

## Шаг 3. Сеть или проект удалён

* `status=network` / `timeout` — контейнер на Timeweb не может соединиться с
  `*.supabase.co`: чаще всего это фильтрация трафика из РФ или сбой у провайдера.
  Ключи здесь ни при чём. Что делать: подождать 10–15 минут и обновить
  `/api/health/db`; если не проходит часами — проверить связь из другого места
  (мобильный интернет телефона, <https://ping.pe>) и, при устойчивой блокировке,
  переносить базу или ставить прокси. Настройка `SUPABASE_FETCH_TIMEOUT_MS`
  (например `30000`) помогает только при «медленной», а не отрезанной сети.
* `status=project_missing` — проект удалён или `SUPABASE_URL` указывает на
  старый адрес. Если проект удалён: создайте новый проект Supabase, примените
  `supabase/schema.sql` и миграции из папки `supabase/`, затем обновите
  `SUPABASE_URL` и ключи (шаг 2).

## Шаг 4. Готовый блок переменных окружения (копировать и вставить)

Панель Timeweb Cloud → **Приложения** → ваше приложение → **Переменные окружения**.
Вставьте список ниже и замените всё, что в угловых скобках.

```env
# ── База данных Supabase ────────────────────────────────────
SUPABASE_URL=https://<ваш-проект>.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<Secret key / legacy service_role>
NEXT_PUBLIC_SUPABASE_ANON_KEY=<Publishable key / legacy anon>

# ── Админка ────────────────────────────────────────────────
# Секрет подписи сессий админки: случайная строка 32+ символов.
# Если сменить — все администраторы войдут заново (данные не теряются).
ADMIN_SESSION_SECRET=<случайная-строка-32+символов>
# Путь админки. ОБЕ переменные должны совпадать!
ADMIN_SECRET_PATH=<путь-админки>
NEXT_PUBLIC_ADMIN_PATH=<тот-же-путь-админки>

# ── Сессии клиентов сайта (можно оставить пустым) ──────────
USER_SESSION_SECRET=<случайная-строка-32+символов>

# ── Служебное (нужно для запуска) ──────────────────────────
NEXT_PUBLIC_SITE_URL=https://sibgofrotorg.ru
PORT=3000
SUPABASE_FETCH_TIMEOUT_MS=30000

# ── Загрузка фото товаров ──────────────────────────────────
NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME=<cloud name>
CLOUDINARY_API_KEY=<api key>
CLOUDINARY_API_SECRET=<api secret>

# ── Уведомления о заявках в MAX (необязательно) ────────────
MAX_BOT_TOKEN=<токен бота MAX>
MAX_ADMIN_CHAT_ID=<id чата>
```

### Важные примечания

* **`ADMIN_SECRET_PATH` и `NEXT_PUBLIC_ADMIN_PATH` обязаны совпадать.**
  Если они различаются, вход в панель ломается (страница открывается по одному
  адресу, а вход и проверка сессии ищут её по другому). Диагностика показывает
  такое расхождение отдельной строкой.
* **Переменные `NEXT_PUBLIC_*` «запекаются» в сборку.** После их изменения нужен
  **пересбор** («Пересобрать и запустить»), а не просто перезапуск. Остальных
  переменных достаточно перезапуска.
* Порядок действий после правки переменных:
  **Сохранить → Пересобрать и запустить → подождать 3–5 минут → обновить админку**.
* Секрет (`ADMIN_SESSION_SECRET`) можно сгенерировать здесь:
  <https://www.uuidgenerator.net/> (возьмите два UUID подряд) или командой
  в терминале: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.

## Шаг 5. «Неверный логин или пароль», «Сессия истекла», аккаунта нет

Сначала посмотрите `/api/health/db` — если там не `ok`, дело не в пароле,
вернитесь к шагу 1/2. Если база в порядке, значит проблема в сессии или аккаунте.

### 5.1. Истёкшая сессия (самый частый случай)

Сессия администратора — это JWT в cookie `admin-session`. Она живёт 30 дней и
**продлевается автоматически**, пока вы работаете в панели. Если сессия всё-таки
истекла (например, сменился `ADMIN_SESSION_SECRET` или почистили cookie браузера),
админка сама приведёт на страницу входа с надписью **«Сессия истекла»**.

Что делать: **просто войдите заново** тем же логином и паролем — «обновлять» JWT
вручную не нужно. Если хочется выйти принудительно — кнопка выхода в панели
(или очистите cookie для домена в настройках браузера).

Чтобы не вылетать принудительно, не меняйте `ADMIN_SESSION_SECRET` без нужды:
смена этого значения разлогинивает всех сразу.

### 5.2. Аккаунта нет или пароль забыт — восстановление без SQL

В проекте есть одноразовый аварийный вход. Он выключен по умолчанию.

1. В переменные окружения добавьте (шаг 4), сгенерировав строку 32+ символов:

   ```env
   ADMIN_RECOVERY_TOKEN=<случайная-строка-32+символов>
   ```

2. **Перезапустите** приложение.
3. Откройте в браузере:

   ```
   https://sibgofrotorg.ru/api/health/recover-admin
   ```

4. В форме укажите токен, логин (`owner`), новый пароль (8+ символов) и роль
   (`owner` — полный доступ). Нажмите **«Восстановить доступ»**.
5. Войдите в админку новым паролем.
6. **Удалите `ADMIN_RECOVERY_TOKEN`** из переменных окружения и перезапустите
   приложение — «дверь» закроется.

Указать токен можно и через терминал (если он доступен):

```bash
curl -X POST https://sibgofrotorg.ru/api/health/recover-admin \
  -H "Content-Type: application/json" \
  -d '{"token":"<ADMIN_RECOVERY_TOKEN>","username":"owner","password":"<новый пароль>","role":"owner"}'
```

### 5.3. Через SQL (если форма недоступна)

Supabase → **SQL Editor** → **New query**. Проверить администраторов:

```sql
select username, role, is_active, (password_hash is not null) as has_password, created_at
from admins
order by created_at;
```

Если таблицы `admins` нет вовсе — создайте её:

```sql
create table if not exists admins (
  id uuid primary key default gen_random_uuid(),
  username text not null unique,
  password_hash text not null,
  role text not null default 'admin'
    check (role in ('owner', 'admin', 'manager', 'lawyer', 'wastepaper')),
  display_name text default '',
  is_active boolean default true,
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);
```

Если база не знает роль `owner` (ошибка CHECK при вставке) — расширьте ограничение:

```sql
alter table admins drop constraint if exists admins_role_check;
alter table admins add constraint admins_role_check
  check (role in ('owner', 'admin', 'manager', 'lawyer', 'wastepaper'));
```

Пароль в базе хранится только в виде scrypt-хеша (`соль:хеш`). Готовый SQL с
хешем выдаёт команда в проекте:

```bash
npm run admin:sql -- --username owner --role owner
```

(затем вставьте полученный `insert … on conflict …` в SQL Editor). Либо
воспользуйтесь формой из пункта 5.2 — она делает то же самое без SQL.

## Шаг 6. Что-то ещё: пустые разделы, ошибки по таблицам

1. Откройте `/api/health/db?deep=1` — блок `tables` перечисляет базовые таблицы.
   Если таблица помечена как `missing` — примените SQL-миграции из папки
   `supabase/` (Supabase → **SQL Editor** → вставьте содержимое файла → **Run**).
   Начинать всегда со `schema.sql`, затем файлы `migration_*.sql`.
2. В админке откройте **Диагностика** — там видно счётчики строк по таблицам.
   Если `products: 0`, `settings: 0` при работающей базе — вы подключились к
   другому проекту Supabase (проверьте `SUPABASE_URL`).

## Шаг 7. Проверка, что всё починилось

1. `/api/health` → `{"ok":true}`.
2. `/api/health/db` → `"status":"ok"`, HTTP 200.
3. `https://sibgofrotorg.ru/<путь-админки>/diagnostics` → все галочки зелёные,
   «Переменные окружения» без красных строк.
4. Вход в админку проходит, разделы открываются, в правом верхнем углу нет
   красной полосы «База данных недоступна».

## Частые вопросы

**Почему сайт работает, а админка — нет?**
Публичные страницы отдаются из кэша (ISR: до 2 минут и далее — последняя удачная
версия), поэтому сбой базы на них не виден сразу. Админка же ходит в базу при
каждом запросе, поэтому падает первой. Это не два разных сбоя, а один.

**Как «обновить JWT» администратора?**
Никак вручную — сессия продлевается сама, а по истечении достаточно войти
заново. Кнопки «обновить токен» нет и не нужно: JWT живёт в cookie и не хранится
в базе.

**А ключи Supabase (service_role) истекают?**
По времени — нет. Они перестают работать только если в проекте нажали
**Rotate JWT secret**, отключили legacy-ключи или проект удалён/на паузе. Это
лечится шагами 1–2.

**Где смотреть логи ошибок?**
Timeweb Cloud → приложение → **Логи**. Ищите строки `Read admin nav layout error`,
`Get supply plans error`, `Admin notifications error`, `Login error` — рядом
будет текст ошибки базы. В браузере причина видна на `/api/health/db` и в
разделе «Диагностика».

**Админка пишет «Unauthorized» / «Сессия истекла» на всех запросах.**
Значит истекла или не читается cookie сессии: войдите заново. Если после входа
сразу то же самое — проверьте, что `ADMIN_SESSION_SECRET` задан и не короче
32 символов (Диагностика это показывает), и что `ADMIN_SECRET_PATH` совпадает
с `NEXT_PUBLIC_ADMIN_PATH`.

**Я сменил `ADMIN_SECRET_PATH` — старые ссылки в закладках не работают.**
Это ожидаемо: путь админки изменился. Заодно смените его в закладках. Помните,
что `NEXT_PUBLIC_ADMIN_PATH` требует пересборки.

## Что сделано в коде, чтобы такого «молчаливого» сбоя больше не было

* `GET /api/health/db` и `?deep=1` — человеческий диагноз вместо `supabase_unreachable`;
  `node scripts/doctor.mjs` — тот же диагноз в терминале.
* Новый раздел админки **Диагностика** (`/{путь}/diagnostics`, только owner/admin).
* Красная полоса «База данных недоступна» над содержимым панели с кнопками
  «Проверить снова» и «Диагностика» — вместо десятка разных ошибок в разделах.
* Ошибка рендера админки теперь объясняется человеческим текстом
  (`[adminPath]/error.tsx`), а не «An error occurred in the Server Components render».
* Вход в админку при недоступной базе отвечает **503 «База данных недоступна»**
  и не выдаёт текст «Неверный логин или пароль» — пароль тут действительно ни при чём.
* Истёкшая сессия: API отвечает 401 с кодом `session_expired`, интерфейс сам
  ведёт на страницу входа с надписью «Сессия истекла» (раньше просто сыпались
  ошибки в каждом разделе).
* Сессия продлевается автоматически (30 дней, продление раз в 12 часов активности).
* Путь админки читается одним модулем (`src/lib/admin-path.ts`) во всех 50 файлах:
  расхождение `ADMIN_SECRET_PATH` / `NEXT_PUBLIC_ADMIN_PATH` больше не может
  «развести» страницу входа и проверку сессии.
* Аварийное восстановление доступа без SQL: `ADMIN_RECOVERY_TOKEN` +
  `/api/health/recover-admin` (по умолчанию выключено).
