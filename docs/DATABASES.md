# Источники данных и копии на ПК

Приложение сейчас работает с одним выбранным Supabase. Подключения задаются в
`.env`: `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` — источник #1,
`SUPABASE_SECONDARY_URL` и `SUPABASE_SECONDARY_SECRET_KEY` — источник #2.
По целевому плану #1 — Beget, #2 — supabase.com, но фактические URL зависят
от настроенного окружения. Изменение шаблона `.env.example` не переключает
существующие установки; проверьте реальные адреса и ключи перед переключением. Поддерживаются
старые и новые форматы ключей; секреты нельзя публиковать. VPS должен быть
полноценным Supabase с PostgREST. Ключи и настройки сервера используются только
на сервере, не передаются в браузер.

**Переключение источника пока общее для сайта**, не отдельное для каждого ПК.
Переключение не копирует данные; сначала убедитесь, что выбранная база актуальна.
Автоматический переход на другой Supabase может показать устаревшую базу;
запись и RPC в автоматически выбранный резерв заблокированы до явного выбора
рабочей базы. Это не доказывает, что резерв актуален. Автопереход на JSON-файл сервера отключён.

Серверные автокопии, локальное зеркалирование, импорт в серверную JSON-БД и
аварийный вход через загрузку файла на сервер отключены. Если раньше на сервере
уже был `local-db.json`, он **не удалён**: владелец может скачать его для
проверки. Если в нём есть несинхронизированные изменения, не переключайте
источник до их сохранения и проверки. Старый серверный локальный режим остаётся
только для чтения, чтобы не уничтожить возможные старые данные. Никаких файлов
с сервера автоматически не удаляем.

На каждом ПК сайт, запущенный через `npm run dev`, может хранить и обновлять
свой JSON-файл; тот же файл используется для ограниченного локального просмотра.
Полноценная офлайн-запись и объединение изменений не реализованы и сейчас не
требуются. Сервер сайта Timeweb не может сам открыть диск Z: или Downloads ПК:
для него действует отдельный браузерный способ сохранения.

## План работы админки без интернета

Целевой сценарий: на каждом рабочем ПК заранее установлены Node.js,
зависимости и собранное приложение, затем сайт запускается **на самом ПК**.
Этот локальный сервер может обращаться к файлам своего диска или разрешённой
папке Z:, в отличие от сайта на Timeweb. Пока интернет есть, исходные данные
нужно заранее получить из выбранного Supabase. При полном отключении сети
нельзя получить новые данные из Supabase и нельзя автоматически объединить
изменения, сделанные в это же время на других ПК.

Реализация ещё не завершена: экспериментально подключены парольный вход и
чтение части данных, **без записи и синхронизации**. Перед отключением сети
нужно запустить сайт локально, войти владельцем и в разделе «База данных»
подготовить снимок из доступного Supabase или выбрать ранее сохранённый полный
JSON, затем выбрать его просмотр. Для новой установки сайт пробует папку Downloads
автоматически; при необходимости владелец указывает другую существующую папку.
Импорт файла доступен только вошедшему владельцу на сайте этого ПК, не является
беспарольным входом и ограничен 200 МБ через интерфейс. Если автообновление или
журнал не включены, снимок создаётся один раз и устаревает.
Даже с обновлением это не рабочая офлайн-БД; проверяйте дату данных.

Сайт запускается на этом ПК обычной командой `npm run dev`; отдельный сервер
БД не нужен. Команда ограничивает доступ localhost и включает локальные функции
сайта. Если на ПК ещё нет настройки, после входа владельца сайт пробует создать
`Downloads/pc-<UUID>/sgt-working-db.json` из активной Supabase; при наличии
журнала этот же файл обновляется. Он же затем читается в локальном режиме.
Путь Downloads по умолчанию — `~/Downloads`; если системная папка перенесена,
нужно указать существующую папку в админке или `SGT_PC_DOWNLOADS_DIR` в локальном
окружении. Настройки хранятся в профиле данного ПК, не на Timeweb. Ранее выбранные
папки и настройки автообновления не переопределяются. Старый запуск `dev:pc` и
`start:pc` остаётся совместимым: это варианты запуска того же сайта, не БД.

Код, зависимости и действующий `ADMIN_SESSION_SECRET` длиной не менее 32 символов
должны быть подготовлены заранее; даже в `npm run dev` известная тестовая заглушка
для локального режима не применяется.
Первый снимок и переключение в режим просмотра требуют авторизованного владельца;
при отключении Supabase без уже действующей сессии безопасный первый офлайн-вход
не гарантирован. До аварии включите и проверьте локальный просмотр и вход. При
просмотре RPC и запись отклоняются; некоторые сложные запросы и представления
не поддерживаются, сравнение и сортировка могут отличаться от PostgreSQL.
Переключение режима требует нового входа; пароль и права берутся из снимка и не
обновляются офлайн. Внешние файлы, Supabase Auth и Storage не входят в копию.
Снимок содержит персональные данные и хеши паролей: защитите папку Downloads и
профиль ПК. Файл и архивы на Windows/Z: и нагрузка больших JSON не проверены.

Сетевой dev-сайт без локального режима можно отдельно запустить через `dev:plain`;
локальный PC-режим намеренно не предоставляет файлы через сетевой адрес. Для
Timeweb приложение использует браузерную копию: без выбранной папки браузер может
заблокировать загрузку и не может автоматически перезаписать тот же файл. Данные
браузера Timeweb и локального сайта разделены по origin; заранее импортируйте или
подготовьте снимок локального сайта, если нужен локальный просмотр.


### Обновление локального снимка и локальные архивы

Для нового ПК в режиме `npm run dev` начальная копия и автообновление
подготавливаются автоматически после входа владельца. Если журнал ещё не готов,
создаётся только начальный снимок, показывается предупреждение, а повторная
проверка журнала выполняется не чаще раза в минуту; большие полные снимки не
запрашиваются постоянно. Для ранее настроенного ПК действуют прежние настройки;
автообновление можно явно включить. Владелец отдельно готовит триггеры журнала
кнопкой в разделе «База данных» на каждой нужной Supabase после установки миграций.
Смена существующего чистого снимка вручную требует подтверждения. Он также
запоминает идентификатор источника. Далее при открытой вкладке админки владельца
на локальном сервере изменения проверяются примерно каждые 5 секунд. Получаются
изменённые строки и удаления; файл JSON физически переписывается при изменениях,
но не переписывается только из-за очередного опроса. Изменения в других источниках
в этот снимок не попадают. В режиме локального просмотра и при отсутствии вкладки
обновление не выполняется. Повреждение файла, независимые локальные изменения,
смена источника, сброс журнала или смена режима останавливают замену. После
сброса требуется повторное явное подтверждение полного снимка; смена идентификатора
источника дополнительно блокирует повторное включение. При долгом отсутствии
изменений курсор на диск не переписывается и после очистки журнала может
потребоваться повторный полный снимок. Журнал создаёт нагрузку на Supabase,
продолжает расти при отключённых вкладках, и его следует предварительно испытать
на тестовой БД. Это не дублирование локальных изменений в Supabase.

На новом ПК архивы включены по умолчанию; у ранее настроенных ПК их можно включить
отдельно. Сайт на ПК, пока
запущен, сохраняет файлы в `pc-<UUID>/scheduled` в 18:00 и 23:00 по Новосибирску,
в том числе без интернета. Окно каждого запуска — 10 минут; если сервер или диск
недоступен всё это время, архив пропускается. Существующий файл не заменяется;
для атомарного создания используется hard link, поэтому на некоторых дисках и
SMB/Z: создание может завершиться ошибкой. Ошибка показывается в панели, а
поведение Windows, SMB и восстановление после потери питания ещё не проверены.
Архив — это полный снимок `public`, а не очередь независимых изменений; он
содержит персональные данные и хеши паролей, ограничьте доступ к папке. Это
отдельно от ранее реализованных браузерных архивов Supabase.

### Ручной выбор и смена папки Z:

На локальном сервере владельцу в «База данных» можно вручную указать
существующий путь (например, `Z:\СибГофроТорг` или локальную папку дома).
Диск Z: должен быть заранее подключён в Windows: приложение не создаёт сетевое
подключение и не получает доступ к диску через Timeweb. У каждого ПК собственный
идентификатор и подпапка. Кнопка смены папки копирует рабочий файл с проверкой;
старый файл и старые архивы не удаляются и не переносятся. Уже существующий
иной файл никогда не заменяется. Если hard link недоступен, используется
эксклюзивное создание нового файла; при отключении питания может остаться
неполный файл в новой папке, а старая настройка и исходный файл сохранятся.
В таком случае нужна ручная проверка, прежде чем убирать неполный файл.
Перенос и блокировки на реальном Windows/Z:/SMB пока не испытаны.

### Экспериментальный SQL-примитив объединения

Новая отдельная миграция `migration_pc_merge_apply.sql` включена и в полный
скрипт. Она добавляет ограниченный RPC для одной Supabase: проверка источника,
каталога и исходных значений, транзакционное применение с активными триггерами,
проверка конечных строк и квитанция для безопасного повтора с тем же ID.
Функция доступна только `service_role`, не подключена к интерфейсу и не запускает
синхронизацию сама. Она блокирует запись в таблицы на время применения (ожидание каждой блокировки
ограничено 5 секундами); максимум 500 изменений и 10 МиБ. `admins`, `users` и
таблицы с последовательностями намеренно не поддерживаются. Надёжность при
реальных конкурентных транзакциях, отказах и разных серверах не доказана; это
не распределённая транзакция и не полноценное двустороннее объединение.
Отдельно исправлен порядок полной миграции и её промежуточные ограничения для
повторного запуска с уже существующими ролями и статусами; тест выполняется
только на изолированном PGlite, не на реальном Supabase.

Установка `SGT_PC_LOCAL_SERVER=1` без локального запуска и настройки не включает
офлайн-работу. Файловое хранилище создаёт отдельный файл `pc-<UUID>/sgt-working-db.json` на заранее
существующем выбранном диске: исходный снимок и рабочие данные находятся в
одном файле. Он не перезаписывает существующий файл при создании, проверяет
контрольные суммы и версию и использует файл блокировки для согласованных
процессов. Проверена конкуренция двух процессов в тестах; реальный сетевой Z:,
Windows и поведение при потере питания не проверены. Нельзя считать блокировку
гарантированной на всех сетевых файловых системах. При оставшейся после сбоя
блокировке запись останавливается, без автоматического её удаления.

Отдельный предварительный план сравнивает строки по настоящим первичным ключам
из каталога схемы. Конфликтующие правки, таблицы без ключа и изменения
последовательностей требуют разбора. Сам план ничего не записывает и не
гарантирует выполнение внешних ключей и других ограничений PostgreSQL; для
применения потребуются проверка общего предка и транзакционная проверка
актуальных значений целевой БД. Существующий браузерный merge пока работает по
таблицам, а не по этому плану.

При обрыве ответа на запись или RPC сервер больше не повторяет эту операцию на
другой Supabase: первая БД могла успеть её сохранить. Такая операция возвращает
ошибку неопределённого результата; перед повтором нужно проверить исходную БД.
Это не делает существующий автопереход безопасной репликацией: две работающие
независимо базы могут разойтись. Донастройка, полноценная запись админки в локальном режиме, безопасная
синхронизация и гарантированное распознавание актуальности резервов остаются
будущей работой.
