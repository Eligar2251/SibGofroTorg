# Полные копии трёх источников БД

## Область и предпосылки

Один выбранный источник остаётся рабочим. Остальные — реплики, **в них нельзя
независимо вносить изменения**: при обновлении реплики её public-таблицы будут
заменены целиком, включая удаления. Синхронизация не является multi-master,
не выполняется непрерывно и не является журналом транзакций. При сбое и
переключении можно потерять изменения после последнего успешного снимка (RPO).
Не размещайте несколько экземпляров приложения с общими настройками: локальная
база, блокировка операции и планировщик рассчитаны на один процесс сервера.

1. На обоих Supabase установите отдельно
   `supabase/migration_complete_app_backup.sql` (она также входит в
   `supabase/FULL_DATABASE_MIGRATION.sql`). На новом сервере нужна вся схема
   приложения; на существующем применяется отдельная миграция. Таблицы и
   колонки обеих баз должны совпадать. Функции выполняет только `service_role`,
   никому не передавайте секретный ключ.
2. Заполните `.env` адресами и секретными ключами каждого сервера. Переменные
   `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` — Supabase Cloud;
   `SUPABASE_SECONDARY_URL`/`SUPABASE_SECONDARY_SECRET_KEY` — VPS. Активная
   БД выбирается в админке. Директории `SGT_DATA_DIR` и `SGT_BACKUP_DIR` должны
   быть постоянными и доступными серверу для записи; в Docker нужны volumes.
3. Войдите владельцем, откройте **База данных → Полные копии всех таблиц**.
   Отметьте копирование для каждой будущей реплики, укажите интервал (по
   умолчанию 150 секунд) и подтвердите замену. По умолчанию оно выключено.
   Нажмите «Копировать сейчас» и убедитесь, что каждая копия завершилась
   успешно. В статусе приведены время и ошибка каждой базы. Снятая отметка
   прекращает её обновление, но **не останавливает сам процесс PostgreSQL**.
4. Первое успешное копирование в локальную БД сохраняет и описание колонок,
   необходимое для полного бэкапа из локальной БД. Невыгруженные локальные
   правки не перезаписываются: локальное копирование остановится с ошибкой.
   Если локальная БД содержит несовместимые/неполные строки или новые таблицы
   без описания, полный бэкап/репликация остановится с ошибкой, а не будет
   помечен успешным. Перед переводом сайта на резерв выполните синхронизацию,
   прекратите новые записи и проверьте данные; проверки актуальности не заменяют
   блокировку записей или репликацию PostgreSQL.

Автоматический переход возможен даже без успешной локальной копии: сначала включите и проверьте локальную реплику, либо отключите автоотказ в настройках.

Включённое автокопирование переводит автоматический аварийный переход на
**локальную** копию, а не на удалённую реплику: нельзя направлять запись в базу,
которая в этот момент заменяется. При локальной работе невыполненные изменения
сохраняются в очереди и не удаляются только потому, что снимок передан резерву.
Для ручной досинхронизации очереди сначала остановите полное автокопирование, затем проверьте результаты старой операции и данные целевой БД.

## Скачать и восстановить

«Скачать полный бэкап на ПК» делает JSON-снимок текущего рабочего источника:
все обычные и секционированные **таблицы public**, включая новые обнаруженные
таблицы, все строки и описание колонок. Функции/триггеры/политики создаются
миграциями, а не этим JSON. Исключены представления, объекты расширений,
другие схемы (включая Supabase Auth), объекты Storage и файлы Cloudinary.
Копия содержит персональные данные и хеши паролей — ограничьте доступ к файлу.
Это не файл аварийного беспарольного входа. Старый «локальный JSON» на странице
остаётся отдельной частичной копией и не подходит как полный файл нового формата.

При каждом успешном снятии полного снимка планировщиком сохраняется защищённый
файл в `SGT_BACKUP_DIR/full-snapshots`; ротация использует настройку количества
серверных снимков. Это диск **сервера**. Диск домашнего ПК доступен напрямую
только если смонтирован на сервер; при выключенном ПК он недоступен. Открытый
браузер для серверного планировщика не нужен. В serverless/при остановленном
процессе таймер не работает.

Для восстановления остановите автокопирование и на время восстановления
прекратите записи в целевые базы. Выберите нужные базы, загрузите полный файл
нового формата и подтвердите полную замену. Каждая удалённая БД восстанавливается
отдельной транзакцией: если одна упала, остальные не откатываются; результат
показывается для каждой. Значения PostgreSQL sequences могут измениться даже при последующем откате, поскольку `setval` не транзакционен. При несоответствии схем, внешних FK в других схемах,
циклических FK, повреждённом файле или ошибке ограничений восстановление в
конкретную Supabase откатывается. Сначала проверяйте на отдельной тестовой БД.
На локальную БД при подтверждённом восстановлении тоже записывается файл
целиком, включая замену очереди локальных изменений.

Этот формат работает через JSON/PostgREST, а не `pg_dump`: большие данные могут
превысить таймаут/лимит сервера или память; числа за пределами точного
целочисленного диапазона JavaScript отклоняются. JSON не гарантирует сохранение
произвольной точности всех десятичных значений и вложенных чисел. Для финансовых
данных, точного disaster recovery и очень больших баз обязательно дополнительно
настраивайте штатные резервные копии PostgreSQL/Supabase и проверяйте их
восстановление. Секреты среды, файлы и инфраструктура резервируются отдельно.
