# Полный экспорт и восстановление Supabase

На обоих проектах Supabase установите отдельно
`supabase/migration_complete_app_backup.sql` через Dashboard → SQL Editor; она
также включена в `supabase/FULL_DATABASE_MIGRATION.sql`. Схемы должны совпадать.
Функции доступны только серверному `service_role`; ключ нельзя передавать клиенту.

В разделе владельца можно скачать полный снимок таблиц приложения `public` и
восстановить его в выбранный Supabase. Схема, функции, триггеры и политики
создаются миграциями, а не JSON. Supabase Auth, Storage, Cloudinary и другие
внешние файлы не входят. Файл содержит персональные данные и хеши паролей —
ограничьте доступ. Это не файл аварийного входа.

Перед восстановлением остановите автокопирование и все записи в целевые БД.
Таблицы каждой выбранной БД полностью заменяются, включая удаления. Каждая
удалённая БД восстанавливается отдельно: при ошибке одной другие не откатываются.
Проверяйте на тестовой БД. Несовпадение схем, внешние или циклические FK и ошибки
ограничений откатывают транзакцию соответствующей БД; значения sequences могут
измениться даже при последующем откате, поскольку `setval` не транзакционен.

Старый механизм опционального периодического копирования между двумя Supabase
остаётся в коде, но включение убрано из интерфейса базы. Если он уже был включён,
на странице владельца отображается предупреждение и кнопка остановки; при открытии
страницы настройки автоматически не меняются. Механизм копирует полным снимком.
Источник один, запись непосредственно в резерв запрещена: она будет заменена. Реплика может отставать, возможна потеря данных после последнего
снимка. Таймер и блокировка процессные, не рассчитаны на несколько серверов;
операция не обеспечивает fencing и zero-data-loss. Настройка выключена по
умолчанию. Серверные архивы и реплика в серверный JSON отключены; файлы на ПК
создаются отдельно через [настройки ПК](PC-SCHEDULED-ARCHIVES.md).

Этот формат использует JSON/PostgREST, а не `pg_dump`. Большие данные могут
превысить таймаут или память; числа за пределами безопасного целочисленного
диапазона JavaScript отклоняются, произвольная точность десятичных значений не
гарантируется. Для финансовых данных и полноценного disaster recovery нужны
также штатные бэкапы PostgreSQL/Supabase с проверкой восстановления.
