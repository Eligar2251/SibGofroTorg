# Полные архивы на ПК по расписанию

Это резервные копии, а не двусторонняя синхронизация. Офлайн-запись не
реализована. При обычном локальном запуске сайта через `npm run dev` отдельный
JSON на ПК доступен для ограниченного чтения; Timeweb не имеет доступа к нему.

Владелец выбирает папку ПК или Z: в разделе «База данных → Локальная копия и
архивы на этом ПК». Новые профили и старые профили с автоматическим выбором
активной БД по умолчанию копируют обе Supabase. Ранее сохранённый ручной выбор
источников остаётся прежним. Источники в интерфейсе обозначены как №1
(`SUPABASE_URL`) и №2 (`SUPABASE_SECONDARY_URL`); фактические адреса проверяются
в настройках. Для полного снимка каждой Supabase нужны её URL, секретный ключ и
`migration_complete_app_backup.sql`. Для отслеживания изменений дополнительно
нужны `migration_pc_incremental_backup.sql` и подготовка журнала кнопкой
владельца для каждой нужной базы. Установка миграций сама не включает триггеры.

Каждый пользователь в профиле браузера получает собственный случайный каталог
`pc-<UUID>` внутри выбранной папки. В нём отдельные подпапки
`primary/scheduled` и `secondary/scheduled` с файлами по датам. При запуске
сайта на самом ПК сохраняется также снимок локального JSON в `local/scheduled`.
На Timeweb этот файл недоступен. Дополнительный `sgt-full-daily-msk.json`
в каждой папке источника перезаписывается каждый день после 18:00 Москвы. Кнопка «Сохранить текущую копию сейчас» отдельно записывает `sgt-full-current.json` в папку каждого выбранного источника; она не отслеживает изменения автоматически. Настройка и
разрешение привязаны к учётной записи владельца и профилю браузера на конкретном
ПК; это не является защитой файлов от других пользователей этого ПК или диска.
Файлы могут содержать персональные данные и хеши паролей — ограничьте доступ и
учтите, что ротация не настроена: следите за свободным местом.

Нужен HTTPS, Chrome/Edge с поддержкой File System Access API и Web Locks,
открытая вкладка админки с действующей сессией владельца, исправный сайт, сеть
и доступный диск. После перезапуска браузер может потребовать вручную снова
подтвердить доступ к папке. Вкладки одного профиля координируются; разные ПК
пишут в разные папки. Таймер браузера может задерживаться, особенно в фоне:
старые архивы на 18:00 и 23:00 Новосибирска выполняются в первые 10 минут.
Дополнительный ежедневный файл за 18:00 Москвы можно записать позднее, до конца
того же дня по Москве, при первом доступе к диску и БД. Если сайт или вкладка
не работали весь оставшийся день, архив за этот день не создаётся. Ошибки
отображаются в админке.
Проверяйте последнюю дату архива; непрерывность и точное время не гарантируются.

Файл можно импортировать как полный бэкап через соответствующую форму владельца.
При запуске сайта на ПК в режиме Supabase владелец может выбрать один файл и
после подтверждения восстановить его в обе Supabase и локальный JSON. Все три
источника заменяются одинаковым снимком. Сначала локальный JSON, затем базы по
очереди: при ошибке возможно частичное восстановление, автоматического общего
отката нет. Локальное автообновление после этого отключается; включайте его
снова только после проверки. Восстановление заменяет все таблицы выбранной БД; остановите все записи и сначала
проверьте файл на тестовой БД. Схема должна совпадать, а Auth, Storage и внешние
файлы не входят в копию. Формат JSON также имеет ограничения точности чисел и
размера, описанные в `FULL-BACKUP.md`. Старый периодический «локальный JSON» —
другой, потенциально неполный формат, и не заменяет эти полные архивы.

## Сопоставление двух копий

Экспериментальный интерфейс «Сопоставить две полные копии» убран со страницы
базы; соответствующий код не удалён. Принцип работы инструмента: нужно выбрать три файла:
общий исходный полный снимок до независимых изменений и две производные копии.
Сравнение и сборка JSON происходят в браузере; ни одна БД и исходный файл не
изменяются. Сопоставление консервативное: если обе копии по-разному изменили
одну и ту же таблицу или последовательность, оно прекращается. Изменения
разных таблиц и удаления учитываются; в одной таблице разные правки отдельных
строк также считаются конфликтом. Порядок строк в PostgreSQL не считается
изменением. При конфликте нужен ручной разбор, автоматического разрешения нет.

**Общий предок нельзя определить по существующим файлам автоматически.** Если
указать неправильный исходный снимок, файл результата может быть неполным.
Перед выбором убедитесь, что обе копии действительно происходят из него. Связи
между разными таблицами, ограничения, sequences и корректность результата в
целом проверяются при восстановлении в соответствующую схему; сперва
восстановите файл на тестовой БД и проверьте его. Объединение не реализует
рабочую JSON-БД на ПК и не является синхронизацией последних изменений.

## Экспериментальное автообновление текущей копии

**Не развёрнуто и не проверено на реальной рабочей Supabase и сетевом Z:**.
Не включайте на рабочей БД без отдельной проверки на тестовой копии, в том
числе с параллельными и долгими транзакциями, нагрузкой и отключениями сети.
PGlite и имитация браузера не заменяют эту проверку.

Ветка содержит отдельную миграцию `migration_pc_incremental_backup.sql`, также
включённую в `FULL_DATABASE_MIGRATION.sql`. Она требует обновлённую
`migration_complete_app_backup.sql`. При установке миграции триггеры сами не
включаются. После проверки владелец отдельно готовит отслеживание для отмеченных
Supabase кнопкой в админке. Это общая настройка самой БД, не только конкретного
ПК: подготовка меняет триггеры и может блокировать таблицы; выполняйте вне
рабочего времени. Автообновление нового профиля включено по умолчанию; существующие настройки сохраняются.

Для каждого отмеченного источника в своей папке создаётся `sgt-live-current.json`.
Сначала загружается полный снимок, затем примерно раз в 5 секунд запрашиваются
только изменившиеся ключи и актуальные строки. Удаления учитываются. Если данные
не изменились, файл не переписывается; при изменении единственный JSON физически
перезаписывается целиком. Длительная транзакция, массовая операция, смена схемы,
восстановление, таблицы без первичного ключа или отставание могут потребовать
повторного полного снимка. При добавлении таблиц/партиций могут потребоваться
повторная подготовка триггеров и новый снимок. При смене самой Supabase файл
не перезаписывается; сохраните его и выберите новую папку. Идентификатор БД
может сохраниться при её полном клонировании, поэтому при переносе или замене
проекта всегда выбирайте новую папку вручную. При внешнем
изменении файла автоматическая запись останавливается. Не редактируйте этот
файл вручную и не клонируйте профиль браузера на другой ПК: Web Locks не
является межмашинной блокировкой общего диска.

После подготовки Supabase хранит журнал ключей изменений, пока триггеры
включены, даже если все ПК выключили автообновление. Это дополнительная нагрузка
на каждую запись. Очистка запускается только активными запросами ПК, не чаще
раза в пять минут на процесс сервера, удаляет до 2000 безопасных записей старше
семи дней. При выключенных ПК, большом потоке изменений или долгих транзакциях
журнал может расти неограниченно: необходимы мониторинг и дальнейшая доработка
retention до промышленного использования. Отключение автообновления на ПК
**не отключает** триггеры и журнал в Supabase. Владелец может отдельно остановить
журнал для выбранного Supabase кнопкой в админке: это остановит отслеживание
для всех ПК; старые записи журнала и файлы сохраняются, а при следующем
включении потребуется новый полный снимок. Прямое отключение триггеров,
репликационный режим и внешние изменения последовательностей не отслеживаются
надёжно. Сохранение в сеть, восстановление и точность архивов не гарантируются;
ограничения обычного полного бэкапа применяются и здесь. Не удаляйте исходные
БД и не рассматривайте эту функцию как готовую рабочую JSON-БД.

## Копия без выбранной папки (экспериментально)

Для нового профиля браузера владельца включены автообновление и расписание;
по умолчанию выбираются обе Supabase, снимки сохраняются отдельно. Можно
вручную выбрать одну базу или активный источник. Сохранённый ручной выбор
источников сохраняется; старый автоматический выбор переключается на обе базы. Сайт назначает этому аккаунту/профилю
случайный ID независимо на каждом ПК. Нужны открытая вкладка админки владельца,
работающий сайт и действующая авторизация. Без вкладки запись не выполняется.

Если папка не выбрана, после первого снимка и при изменениях сайт запрашивает
скачивание отдельного JSON; для архивов в 18:00 и 23:00 Новосибирска и
ежедневного снимка в 18:00 Москвы запрашивается отдельная загрузка.
Браузер выбирает место загрузки, может блокировать множественные автоматические
загрузки или запросить разрешение. Он может переименовать файлы или сохранить их
не в Downloads; сайт не может проверить, что они действительно записаны. Статус
«запрошена загрузка» и отметка расписания **не подтверждают сохранение** и не
повторяют попытку для этого окна: при необходимости скачайте копию вручную.
Уникальные имена не гарантируют единственный файл, очистки и ротации нет.

Текущий JSON и курсор изменений сохраняются также в IndexedDB данного origin и
профиля браузера. Это отдельная копия от каталога локального Node-сервера:
Timeweb и localhost имеют разные origin и не видят IndexedDB друг друга. Доступ к
IndexedDB, Web Locks, Web Crypto (HTTPS или localhost) и достаточно места
обязательны; при ошибке хранилища автообновление останавливается. Системная
очистка данных браузера/приватный режим могут удалить копию. Она содержит те же
персональные данные и хеши паролей, что и скачанные файлы; используйте защищённый
профиль и диск, не используйте общедоступный компьютер. В этой вкладке можно
вручную скачать последнюю копию браузера даже при недоступной Supabase; сам сайт
должен быть уже открыт и интерфейс доступен. Удаление копий и управление дисковым
пространством выполняются пользователем.

Для начального снимка нужна `migration_complete_app_backup.sql`; для обновления
изменений также нужна `migration_pc_incremental_backup.sql` и явная подготовка
глобальных триггеров кнопкой владельца. Если журнал не готов, запрашивается
один начальный полный снимок; изменения не отслеживаются, админка показывает
предупреждение и периодически повторяет попытку подключить журнал без постоянной
загрузки полных снимков. После подготовки журнала загружается новый снимок.
Предварительно испытайте эту функцию на тестовой БД, поскольку её влияние на
рабочую PostgreSQL и большую базу не измерено. Если ранее выбранная папка стала
недоступна, автоматического перехода в Downloads нет: надо восстановить разрешение.

Для ограниченного просмотра данных без Supabase заранее запустите сайт на ПК
через `npm run dev` в онлайн-режиме под авторизованным владельцем, дождитесь
подготовки рабочего снимка и проверьте локальный вход до аварии. Отдельный сервер
БД не используется. На новом ПК по умолчанию файл находится в Downloads; сам
сайт обновляет и затем читает тот же `sgt-working-db.json`. Файлы загрузок
можно импортировать в подготовленный локальный сервер только под уже действующей
локальной owner-сессией. Простое скачивание не настраивает локальный сервер,
не обеспечивает первый офлайн-вход и не делает сайт полноценной офлайн-БД.
Запись офлайн и обратная синхронизация в этой задаче не добавлялись.
