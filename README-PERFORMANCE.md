# Производительность: что сделано и что дальше

Цель — «чтобы всё летало» на мониторах 120 Гц. Ниже: что уже сделано, реальные
замеры и приоритизированный список дальнейших шагов с честной оценкой риска.

---

## 1. Что сделано сейчас (без изменений логики)

| Изменение | Почему это тормозило | Где |
|---|---|---|
| Убран `will-change: transform, box-shadow` с карточек товара | В сетке каталога десятки карточек, и каждая постоянно висела отдельным GPU-слоем: лишняя видеопамять и работа композитора на каждый кадр прокрутки. К тому же `box-shadow` не композитится — подсказка была бесполезной | `globals.css`, `.pcc` |
| Убран `backdrop-filter: blur(10px)` с плавающего баннера мессенджеров | Элемент `position: fixed` на всех страницах сайта: браузер пересчитывал размытие области под ним **каждый кадр** прокрутки. Фон и так был непрозрачен на 94% — визуально разницы нет | `globals.css`, `.messenger-float` |
| Убран `backdrop-filter: blur(8px)` с липкой панели массового редактора | То же самое для `position: sticky` в админке | `admin.css`, `.bulk-footer` |
| `loading="lazy" decoding="async"` у картинок в длинных списках админки | Таблица товаров грузила **все** миниатюры сразу: на каталоге в 300 позиций — 300 запросов и 300 декодирований при открытии страницы | список товаров, акции, «под заказ», подбор коробки, генератор фото |
| `useDeferredValue` + `useMemo` в поиске по товарам | Каждое нажатие клавиши синхронно перефильтровывало массив и перерисовывало всю таблицу. Теперь буква появляется мгновенно, таблица догоняет с низким приоритетом | `ProductListClient` |
| Удалена зависимость `lenis` | Библиотека кастомного «плавного скролла» лежала в зависимостях, но не импортировалась ни разу. И хорошо: именно такие библиотеки чаще всего и ломают ощущение 120 Гц, подменяя нативную прокрутку интерполяцией под 60 кадров | `package.json` |

Раньше (в прошлых итерациях) также убраны: опрос журнала действий каждые 5 секунд
по 500 строк, двойной опрос тяжёлого `/api/admin/notifications` каждые 30 секунд,
полная перерисовка страницы «Учёт» после каждого перетаскивания выплаты.

## 2. Замеры (сборка `pnpm build`)

```
.next/static/chunks         3.8 МБ всего
  464 КБ   WarehouseManager  ← модуль «Учёт», один кусок
  448 КБ   общий вендорный чанк
  224 КБ
  196 КБ   html2canvas       ← уже грузится лениво, только при печати
CSS
  272 КБ   admin.css и соседи (33 500 строк)
  128 КБ
  108 КБ
```

Что уже сделано правильно и трогать не надо:
- CSS админки подключён в `layout` админки, а не в корневом — посетители сайта
  эти 272 КБ не скачивают;
- тяжёлые библиотеки (`html2canvas`, `@zxing`) импортируются динамически;
- `xlsx` используется только на сервере и в браузер не попадает;
- все слушатели `scroll`/`resize` — `passive`;
- в `admin.css` уже есть секция «ПРОИЗВОДИТЕЛЬНОСТЬ 60–120 FPS» с
  `content-visibility` для дашборда и списка заявок.

## 3. Что дальше — по соотношению «эффект / риск»

1. ✅ **`useDeferredValue` в больших списках** — товары, склад и заказы в «Учёте»
   (общее поле поиска), клиенты. Ввод больше не ждёт перерисовку таблиц.
2. ✅ **Оставшиеся `<img>` переведены на `loading="lazy" decoding="async"`** —
   закупки, генератор фото.
3. ✅ **`transition: all` убраны** — заменены на явные списки свойств.
4. ✅ **Починены 2 ошибки линтера** в `SalaryBlankPrint.tsx` (сложные выражения
   в зависимостях `useMemo`) — `pnpm lint` теперь чистый.

Осталось из безрискового:

5. **`contain: content` на повторяющихся карточках** админки — браузер перестанет
   пересчитывать раскладку всей страницы при изменении одной карточки. Нужна
   аккуратность с выпадающими меню внутри карточек.

### Средний риск, самый большой выигрыш

5. ✅ **«Учёт» разбит на вкладки через `next/dynamic`** — сделано.
   Было: один клиентский чанк на 464 КБ, браузер парсил и гидрировал все
   вкладки, даже открыв одну. Стало: **232 КБ**, остальное подтягивается
   в момент открытия вкладки. Лениво грузятся зарплаты, автораспределение
   ЗП, отчёты, перевозки, планы поставок, закупки, прогноз, план продаж,
   клиенты, товар на реализации, ревизия склада и модалка инкассации —
   всё это и раньше рендерилось только при активной вкладке, поэтому
   поведение не изменилось.

   Побочный эффект, ради которого это и пришлось делать срочно: dev-сервер
   падал на компиляции этой страницы с «JavaScript heap out of memory»
   в воркере Turbopack. Теперь компилируется за ~4 секунды.
6. **Виртуализация длинных таблиц** (товары, сделки, платежи): рендерить только
   видимые строки. При 500+ строках это разница между 30 и 120 кадрами при
   прокрутке. Риск: ломается `Ctrl+F` по странице и печать — нужно предусмотреть
   режим «показать все» для печатных форм.
7. **Серверная пагинация вместо «загрузить всё».** Страница `/warehouse` на каждый
   рендер тянет остатки, поступления, сделки, платежи, зарплаты, контрагентов,
   перевозки, инкассации, планы, плюс 500 заказов и 200 пользователей. Это и время
   до первого байта, и объём HTML. Риск: заметная переделка запросов.
8. **Разбить `admin.css`** (33 500 строк) по маршрутам — сейчас все стили всех
   модулей грузятся на любой странице админки.

### Точечно под 120 Гц

9. **Пресет «Производительность» в теме админки.** В `AdminTheme` уже есть режим
   пониженной анимации (`data-admin-anim="reduced"`). Можно включать его
   автоматически по `matchMedia('(update: slow)')` или
   `navigator.hardwareConcurrency <= 4` — на слабых машинах интерфейс сразу
   станет резче.
10. **Проверить длительности анимаций.** Всё, что длится 0.2–0.3 с на
    `transform/opacity`, на 120 Гц выглядит отлично; проблема возникает только у
    анимаций `width/height/top/left` — в текущем CSS таких в ключевых кадрах нет,
    но при добавлении новых стоит держать правило «только transform и opacity».

## 3.1. Память dev-сервера

`pnpm dev` запускается через `scripts/dev.mjs`, который поднимает кучу Node
до 8 ГБ (`NODE_OPTIONS=--max-old-space-size`). Именно переменной окружения,
а не флагом: воркеры Next наследуют окружение, но не флаги родителя.

Переопределить: `SGT_DEV_MEMORY=12288 pnpm dev`.
Запустить без обёртки: `pnpm dev:plain`.

## 4. Чего делать НЕ надо

- **Не возвращать библиотеки «плавного скролла»** (lenis, locomotive и подобные).
  Нативная прокрутка в браузере уже синхронизирована с частотой монитора и на
  120 Гц идёт в 120 кадров. Любая JS-интерполяция это ломает.
- **Не расставлять `will-change` «на всякий случай»** — каждый такой элемент это
  отдельный слой композитора. Оправдан он только для одного-двух элементов,
  которые действительно анимируются постоянно (сейчас это сайдбар админки).
- **Не добавлять `backdrop-filter` к `fixed`/`sticky` элементам** — самый дорогой
  эффект при прокрутке.
