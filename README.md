# SibGofroTorg — Каталог и панель управления

Современный веб-сайт и панель управления для оптово-розничной торговли, построенный на **Next.js 16 (App Router + Turbopack)**, **React 19**, **Tailwind CSS v4** и **Supabase (PostgreSQL)**.

---

## 🚀 Деплой

### 1. Деплой в Timeweb Cloud (App Platform / Docker)

Проект полностью настроен для запуска в **Timeweb Cloud** и других облачных платформах как через автосборку (Cloudpack / Nixpacks), так и через `Dockerfile`:

- **Порт и хост**: Приложение запускается на `0.0.0.0` и слушает порт из переменной окружения `${PORT:-3000}`.
- **Команда запуска**: в образе есть универсальный entrypoint (`scripts/docker-entrypoint.sh`), поэтому **в панели Timeweb команду запуска лучше вообще не задавать** — сработает `CMD` из Dockerfile. Если поле обязательное — укажите `node server.js`.
- **Restart-loop на автосборке Timeweb (`Cannot find module '/app/pnpm'`)**: автобилдер Timeweb игнорирует `Dockerfile` из репозитория и генерирует свой образ, включая corepack/pnpm **только в builder-слое**. В runtime-слой pnpm не попадает, а автоопределённая команда запуска для проекта с `pnpm-lock.yaml` — `pnpm start`, которую платформа исполняет как `node pnpm start` из `/app`. Итог — `MODULE_NOT_FOUND` и бесконечный перезапуск контейнера. Исправлено файлом-прокси **`pnpm` в корне репозитория**: он попадает в `/app` при копировании сборки и передаёт запуск в `scripts/start.mjs`. Альтернатива без шима — пересоздать приложение в Timeweb с типом сборки «Dockerfile» (тогда используется наш `Dockerfile`) или прописать команду запуска `node scripts/start.mjs` вручную.
- **Почему раньше был restart-loop**: `Dockerfile` копирует `.next/standalone` **в корень** `/app`, поэтому команда `node .next/standalone/server.js` в Docker-образе падала с `Cannot find module`, а `pnpm start` — потому что `next` CLI не входит в standalone-trace. Теперь обе команды безопасно обрабатываются entrypoint-ом и скриптом `scripts/start.mjs`.
- **Здоровье контейнера**: `GET /api/health` — это liveness, он **не зависит от Supabase** и отвечает `200`, пока процесс жив (раньше health-check падал из-за отсутствующих env-переменных, и платформа перезапускала контейнер). Проверку доступности БД вынесли отдельно: `GET /api/health/db` (503 — если Supabase недоступен/не настроен).
- **Отключение автоинсталляции в проде**: В `pnpm-workspace.yaml` и `.npmrc` явно отключена проверка зависимостей (`verifyDepsBeforeRun: false`, `verify-deps-before-run=never`), благодаря чему `pnpm start` не пытается выполнять `pnpm install` при запуске контейнера; в runner-слой эти файлы и заранее подготовленный corepack-кэш pnpm копируются намеренно.
- **Почему деплой стал быстрее**: `Dockerfile` теперь использует `output: "standalone"` и делает только **одну** установку зависимостей в builder-слое вместо двух.

#### Рекомендуемая конфигурация в панели Timeweb Cloud (сборка из Dockerfile):
- **Команда сборки**: не нужна — всё делает `docker build`.
- **Команда запуска (Start Command)**: оставить пустой (дефолтный `CMD` образа). Если поле обязательное: `node server.js`.
- **Порт (Port)**: `3000` (совпадает с `ENV PORT=3000` в Dockerfile; если поменяете `PORT` в env — поменяйте и порт в настройках приложения).
- **Health check путь** (если настраивается): `/api/health`.
- **Переменные окружения runtime** (обязательные для работы сайта с данными — см. `ENV_GUIDE.md`): `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `ADMIN_SESSION_SECRET`, `ADMIN_SECRET_PATH`, Cloudinary/MAX-ключи. ⚠️ Их отсутствие больше **не** приводит к перезапуску контейнера, но страницы с каталогом будут пустыми, а `/api/health/db` — отвечать 503.

#### Если используете автосборку Cloudpack / Nixpacks (без Dockerfile):

Внимание: штатный автобилдер Timeweb не кладёт pnpm в runtime-слой (см. пункт про `Cannot find module '/app/pnpm'` выше). Для такой сборки в корне репозитории лежит файл-прокси `pnpm` — он перехватывает запуск и передаёт управление `scripts/start.mjs`, поэтому дефолтная автоопределённая команда запуска работает. В репозитории также есть `nixpacks.toml`: install — только через `pnpm` (иначе исторический `package-lock.json` может сбить платформу на `npm install`), старт — `node scripts/start.mjs`, который в такой сборке использует `next start -H 0.0.0.0 -p $PORT`. Порт приложения в панели — `3000` (или тот, что передан в `PORT`).

#### Быстрая диагностика «контейнер перезапускается»

1. `docker logs <контейнер>` (в Timeweb: логи контейнера, а не логи сборки) — ищите `Cannot find module` (неверная команда запуска) или стектрейс env-ошибок.
2. Если статус «unhealthy», а процесс жив — проверьте, что health-check ходит на `/api/health`, а не на страницу, зависящую от БД.
3. Убедитесь, что порт в настройках приложения = порт, который слушает процесс (`node server.js` печатает `- Network: http://0.0.0.0:<PORT>`).

### 2. Деплой на Vercel

В корне репозитория добавлен файл `vercel.json` с настроенными командами для корректной работы с **pnpm v11**:

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "installCommand": "corepack enable && pnpm install --frozen-lockfile --prefer-offline",
  "buildCommand": "pnpm build"
}
```

- **Corepack**: Команда `installCommand` автоматически включает `corepack` и использует версию `pnpm@11.17.0`, указанную в `package.json`.
- **`--frozen-lockfile`**: Vercel использует уже готовый `pnpm-lock.yaml`, без повторного пересчёта дерева зависимостей на каждом деплое.
- **`--prefer-offline`**: если кэш пакетов на стороне Vercel уже есть, установка проходит заметно быстрее.

## 🛡️ Табели охраны: постоянное хранение

Табели охраны теперь автоматически сохраняются в Supabase: сотрудники,
смены и часы по всем месяцам, ручные суммы зарплаты, начисления, дни и суммы
выплат. Повторная генерация месяца и последующие правки обновляют тот же
снимок в БД, не создавая дубликатов. При первом запуске прежние данные из
`localStorage` автоматически переносятся в базу.

Перед первым использованием применить миграцию:
`supabase/migration_duty_schedule_storage.sql`.

В печатной форме зарплата в самом табеле и сводке всегда считается по часам
выбранного календарного месяца. Нижний блок выплат остаётся отдельным и продолжает
использовать выбранный сдвиг 0 / −1 / −2 месяца. Его заголовок задаётся вручную
для каждого месяца, например «Выплаты за июль», и сохраняется вместе с табелем.

## 👤 Карточка клиента: все его заявки

`Админка → Клиенты → «Карточка»` (или прямо `/{admin}/clients/{id}`).

Отдельная страница по каждому пользователю со всеми его обращениями:

- **Что видит клиент.** Рядом со служебным статусом («Новая», «В работе»,
  «Проведена») показана ровно та формулировка, которую человек в этот момент
  читает у себя в кабинете («В обработке», «Сборка заказа», «Готов к выдаче»…).
  Подписи берутся из общего справочника `src/lib/order-status.ts`, поэтому
  админка и кабинет не могут разойтись.
- **Управление на месте:** смена статуса и удаление заявки прямо из карточки,
  теми же кнопками и с теми же проверками, что и в общем списке заявок
  (заявка, ушедшая в учёт, по-прежнему закрывается только через заказ ЗК).
- **Полная история, а не только заказы из кабинета.** Заявки, оформленные
  без входа, но с тем же номером телефона, тоже попадают в карточку — с
  пометкой «без входа». Иначе история клиента выглядела бы неполной.
- **Состав заявки** раскрывается: позиции, количество, цены, адрес доставки,
  комментарий, ссылка на связанный заказ ЗК в учёте.
- **Заявки на макулатуру** этого же телефона показаны отдельным блоком —
  тоже со сменой статуса и удалением.
- Фильтры «Все / В работе / Закрытые» и статистика: сколько заявок, сколько
  выполнено, на какую сумму.

Страница живая: если статус поменял другой менеджер или заявку закрыл учёт
при проведении заказа — карточка обновится сама, без F5.

Миграции не нужны.

## 🚚 Статус «Передано в доставку»

Между «Готов к выдаче» и «Проведена» появился отдельный статус `in_delivery`:
груз передан водителю и едет клиенту. Существующая цепочка не переиначена —
`в работу → готов к выдаче → (передано в доставку) → проведена`, «Выдан» и код
выдачи работают как раньше.

- **Кнопка.** `Заявки → карточка заявки`: «Передано в доставку» доступна из
  «В работе» и из «Готов к выдаче»; обратно — «Вернуть из доставки» (заявка
  снова «Готова к выдаче», дата выпуска снимается). Плюс отдельная плитка
  «В доставке» на главной админки и фильтр в списке заявок.
- **Клиент** видит тот же статус у себя в кабинете («Передано в доставку») с
  плашкой «Заказ передан в доставку». Пока груз в пути, состав заявки и её
  отмена клиенту недоступны — это решение менеджера.
- **Связь с вкладкой «Доставки» односторонне-симметричная**: «Выпущен в
  доставку» в карточке доставки сам ставит заявке `in_delivery` (закрытые,
  отменённые и «выданные» не трогает), кнопка статуса у заявки проставляет
  дату выпуска, а отмена выпуска возвращает заявку «В работу» и снимает дату.
- Закрытие заявки при этом прежнее: либо «Проведена» (если заказ ЗК не
  создавался), либо автоматическое закрытие из учёта после отгрузки.

**Миграция обязательна**: в базе на колонке `orders.status` висит CHECK-
список допустимых статусов, поэтому `in_delivery` без него не сохранится.
Файл — `supabase/migration_order_in_delivery_status.sql` (пересоздаёт
`orders_status_check` полным списком; выполняется мгновенно, данные не
меняются).

## 👀 Кабинет клиента: почему заявки могли «не показываться»

`Админка → Кабинет клиента` (`/{admin}/user-cabinet`) намеренно собран одной
функцией выборки с личным кабинетом клиента (`src/lib/cabinet-orders.ts`), так
что состав заявок у них общий. Три места, где заявки всё-таки терялись, закрыты:

1. **Экран не обновлялся сам.** Он живёт на событиях realtime, а при
   `manual: true` общий хук не делает страховочного опроса — при молчащем SSE
   канала новая (в том числе сегодняшняя) заявка появлялась только после F5.
   Теперь у экрана свой опрос раз в 25 секунд, обновление при возврате
   вкладки из фона, кнопка «Обновить» и отметка «Синхронно с HH:MM:SS».
2. **Клиент находился не по всей базе.** Список клиентов брался как «300
   самых свежих», а поиск фильтровал уже эти 300 — клиента из архива нельзя
   было найти, и экран выглядел пустым. Поиск ушёл на сервер (`ilike` по
   имени, телефону, почте, логину, организации), список отдаёт `total` и
   честно сообщает об обрезке; счётчик заявок больше не считается по
   «последним 2000 заказам на всю базу».
3. **Заявки второго аккаунта скрывались.** Выборка отбрасывала заявки, у
   которых `user_id` не равен выбранному клиенту, — при двух аккаунтах с одним
   телефоном (или если менеджер завёл клиенту новый вход) клиент у себя видел
   всё, а «кабинет клиента» показывал половину. В админском режиме такие
   заявки возвращены с пометкой «другой аккаунт по телефону», гостевые — с
   пометкой «гостевая»; поведение самого клиента не изменено.

Дополнительно: любая выборка заявок теперь идёт с сортировкой «свежие сверху»
и с явным потолком в 1000 строк на запрос; если данных больше, экран говорит
об этом прямо, а не молча режет список. Миграции не нужны.

## 🛒 Закупки: оплата по частям реальными платежами

`Учёт → Закупки`. Закупка больше не «копит виртуальные взносы, которые потом
списываются одной кнопкой». Теперь так:

- **Каждый платёж — отдельная строка банка.** Внесли сумму в карточке закупки —
  в разделе «Банк» появился обычный исходящий платёж. Его видно в общем списке,
  он влияет на баланс и участвует в отчётах.
- **Платежи можно править и удалять** прямо в карточке: дата, сумма, счёт
  (наличные / расчётный счёт / карта ЮМ), «проведён» или «план». Удаление
  убирает платёж и из банка — деньги возвращаются в баланс.
- **Платёж можно завести со стороны банка.** У исходящего платежа появилось поле
  «Закупка»: выбрали — платёж сразу попал в карточку закупки и в её «оплачено».
- **План vs факт.** Снятая галочка «деньги уже ушли» создаёт запланированный
  платёж: он виден в закупке и в банке как ожидаемый, но баланс не трогает,
  пока его не проведут.
- Прогресс закупки считается по **реально оплаченному**: «оплачено X из Y ₽».
- Закупка закрывается кнопкой «Закупка завершена — в архив» и возвращается
  обратно в любой момент.
- Старые виртуальные «отложено» никуда не делись: если они были, показываются
  отдельным блоком «Отложено (старый учёт)», где каждую строку можно провести
  настоящим платежом или удалить.

Миграция: `supabase/migration_purchase_payments.sql`.

## 🏠 Хознужды: списание товара без оплаты

В форме заказа (`Учёт → Заказы`) появился флажок **«Хознужды»**. С ним:

- цены можно оставить нулевыми, итог заказа 0 ₽ больше не ошибка;
- счёт покупателю **не выставляется** — денег по такому заказу не ждут,
  в уведомлениях «отпущено без оплаты» он не появляется;
- склад списывается как обычно, движение товара видно в отчётах;
- в списке заказ помечен значком «хознужды» и не висит вечно в «Активных».

Для образцов, своей упаковки, брака и подарков клиентам.

Миграция: `supabase/migration_deal_internal.sql`.

## 🏢 Учёт аренды (банк аренды)

Отдельный управленческий модуль (`/{admin}/rent`), не связанный со складским банком:

- **Организации**: БАУ и ИП Пакин (свои расчётные счета и балансы), СибИнвестТорг — деньги его арендаторов приходят на счёт БАУ (в интерфейсе есть пометка).
- **Арендаторы**: договор (№ и дата), офис, крайний день оплаты (общий для всех + исключения на контрагента), период оплаты (месяц/квартал/полгода/год/произвольный), отсрочка, безналичный/наличный расчёт.
- **Начисления**: счета за периоды аренды, массовое выставление за следующий период, статусы с учётом отсрочки (ждёт → отсрочка → просрочен).
- **Банк аренды**: балансы (р/с + наличные) по каждой организации, ожидающие и проведённые платежи, история по месяцам.
- **Напоминания**: просрочки и ближайшие оплаты на дашборде аренды, в блоке на главной панели и в колокольчике уведомлений.

Доступ: admin — редактирование; manager — просмотр; lawyer — только дашборд (финансы, просрочки, отчётность).

Перед первым использованием применить миграцию в Supabase: `supabase/migration_rent_accounting.sql`.

## ♻️ Учёт макулатура: виды макулатуры и зарплаты

Отдельный модуль (`/{admin}/wastepaper-account`, доступ admin и роль «макулатура»), деньги
которого не связаны с учётом СибГофроТорг.

- **Виды макулатуры** (вкладка «Виды макулатуры») — единственный справочник видов для приёмок и
  отгрузок: добавление, переименование, цена за кг (подставляется в строку документа), скрытие и
  удаление. Вид без документов удаляется совсем; вид, по которому уже есть приёмки/отгрузки,
  скрывается (старые документы сохраняют название), его можно вернуть. Четыре исходных вида
  (гофрокартон, белая бумага, книги, смесь) сохраняют свои старые коды — прежние документы и
  тарифы калькулятора сайта продолжают работать.
- **Зарплаты** (вкладка «Зарплаты») — та же таблица взаиморасчётов, что в учёте СибГофроТорг
  (план на месяц, долги, дни выплат, график, Excel/PNG), но со счетами модуля: **наличка**,
  **безнал** (оба списываются с остатков макулатуры на дату выплаты) и **сторонние платежи** —
  деньги, не заходившие в кассу/на счёт, с обязательной пометкой, откуда они пришли. Записи живут
  в общей таблице `salaries` с тегами `[Макулатура]` / `[Сторонние:откуда]` и не влияют на банк и
  кассу СибГофроТорг; в финансах модуля они видны расходом по своему счёту. Планы/долги/график
  хранятся в `settings` под ключами `wp_salary_*`.

- **Склад макулатуры** (вкладка «Склад») — остаток по видам: фактически принято − продано по
  действующим документам, плюс ручная правка. Две возможности:
  - **Продажа без списания** — отметка «Не списывать со склада» в карточке сдачи: сумму и оплату
    проводим как обычно, а остаток на площадке **не** уменьшается (груз ушёл не с нашей площадки —
    перегруз, чужой склад). Такой вес не вычитается из остатка, но показывается на складе в графе
    «Продано» строкой «без списания», а в списке продаж сдача помечена бейджем «Без списания».
  - **Ручная правка остатка** — вписываете фактическое количество в последнем столбце вкладки
    «Склад» и жмёте «Сохранить» (так же, как остаток товара в учёте СибГофроТорг). Запоминается
    разница с расчётом по документам, поэтому следующие приёмы и продажи двигают остаток **поверх**
    правки, а не вместо неё; кнопка «Снять правку» возвращает чистый расчёт. Виды, по которым
    документов ещё не было, вписываются отдельной формой под таблицей.
- **Переводы между счетами** (вкладка «Банк», кнопка «Перевод») — переложить деньги из одного счёта
  модуля в другой, указав сумму: например, сняли 50 000 ₽ с безнала в кассу. Перевод проводится
  сразу и показывается в деньгах двумя строками одного документа — расход по счёту-источнику и
  приход по счёту-получателю, поэтому внешний приход/расход модуля не меняется, а остатки счетов
  двигаются. В форме видно, что станет с обоими остатками после перевода, и предупреждение, если на
  счёте-источнике денег меньше суммы (перевести всё равно можно — остаток уйдёт в минус).
- **Пометка «перевозка выполнена»** (вкладка «Приём», колонка «Перевозка») — груз вывезли,
  приём больше не показывается в доставках и очереди перевозок: дальше по нему работают
  только по весу и оплате. Ставится сама, когда завершают рейс с точкой этого приёма
  (вместе с пометкой «ждёт взвешивания»), и вручную — кнопкой ✓ в списке или чекбоксом
  «Перевозка выполнена» в карточке приёма. Сохранение карточки пометку **не** снимает;
  снять её можно тем же нажатием на зелёный бейдж (приём вернётся в очередь).
- **Журнал «Банк»** (отдельная вкладка) — все движения денег модуля в одной выписке: приёмы, сдачи,
  платежи, зарплаты и переводы, с остатком после каждой операции. Фильтры по периоду, счёту,
  поиск, режим «только переводы»; сверху — остатки трёх счетов и их обороты за выбранный период.
  Перевод открывается на правку и удаление прямо из журнала.

Перед использованием справочника видов применить миграцию: `supabase/migration_wp_products_code.sql`
(добавляет `wp_products.code`; до неё исходные виды распознаются по неизменённому названию).

Перед использованием склада с правками применить миграцию: `supabase/migration_wp_stock_manual.sql`
(колонка `wp_shipments.skip_stock` и таблица `wp_stock_adjustments`; до её применения модуль
работает как раньше — продажи списываются, правок нет).

Перед использованием пометки «перевозка выполнена» применить миграцию:
`supabase/migration_wp_transport_done.sql` (колонка `wp_intakes.transport_done` и
перенос пометки на приёмы, которые уже отъездили); до её применения приёмы с пометкой
«ждёт взвешивания» из доставок исчезают, а ручная пометка не сохраняется.

Перед использованием переводов между счетами применить миграцию:
`supabase/migration_wp_account_transfers.sql` (таблица `wp_account_transfers`, RLS, Realtime и
счётчик номеров); до её применения вкладка «Банк» показывает движения без переводов.

## 📈 Прогноз выручки, план продаж и массовая загрузка заказов (Учёт)

Модуль учёта отдела гофротары (СибГофроТорг) дополнен автоматическим планированием:

- **Прогноз выручки** (`Учёт → Прогноз` и свёрнутый блок на дашборде): автоматический план на месяц
  по контрагентам на основе существующих и закрытых (неотменённых) заказов за последние 6 месяцев.
  По каждому контрагенту видно «кто обычно берёт и на сколько»: число заказов, средний чек,
  среднемесячный объём, объём за прошлый месяц, уже оформленное в выбранном месяце и ожидаемую
  сумму. Прогноз намеренно приблизительный — это план, а не точный расчёт. Контрагенты, которые
  не заказывали более 3 месяцев, учитываются только фактически оформленным.

- **План заказов** (`Учёт → План`, отдельная вкладка-таблица): операционный план на месяц по
  правилам классического планирования (скользящее среднее по календарным месяцам за 6 месяцев).
  Таблица «Контрагенты, которые должны сделать заказ»: ожидаемое число заказов, средний чек,
  план выручки, уже оформленное, осталось; раскрывается до списка ожидаемых товаров по каждому
  контрагенту. Таблица «Позиции плана»: сколько потратим товара (план на месяц, уже в месяце,
  осталось к плану), сколько получим денег **с вычетом закупки** — выручка, закупка (план ×
  закупочная цена из карточки товара), маржа, и покрытие склада (хватает / докупить N на сумму).
  План на месяц = среднемесячный объём по истории + уже оформленное в месяце.

- **Копирование заказа**: в карточке заказа (`Учёт → Заказы`) рядом с «Изменить» появилась кнопка
  «Копировать» — открывается форма нового заказа, предзаполненная позициями и реквизитами образца
  (дата — сегодня, оплата — по счёту, без резерва).

- **Массовая загрузка заказов** (`Учёт → Заказы → «Массовая загрузка»` или `/warehouse/import`):
  выбор/ввод контрагента (создаётся автоматически), таблица «дата · товар · количество · цена →
  сумма» с быстрым добавлением строк. Строки группируются по дате: одна дата = один заказ. Заказы
  сохраняются проведёнными с пометкой «архив (импорт)»: склад и банк не затрагиваются, а суммы
  попадают в отчёты и в прогноз выручки.

Перед первым использованием применить миграцию: `supabase/migration_deal_archive_forecast.sql`.

## 💰 Выгода продаж: настройки печати и графики

Раздел `Админка → Выгода продаж` (`/<admin>/profit-report`) печатает план по
выгоде продаж на A4. Перед печатью доступна панель **«Настройки печати»**
(компонент `src/components/admin/ProfitReportPrint.tsx`):

* **Тип отчёта** — «Таблица на лист» или **«Полный отчёт для директора»**
  (многостраничный, см. ниже).
* **Готовые варианты** — «Полный», «Компактный», «Горизонтально»,
  «С графиками», «По продажам» (расшифровка продаж под каждым товаром),
  «Только итоги», «Для директора». Любая правка после выбора варианта
  переводит набор в «Свои настройки».
* **Чёрно-белая печать** — отчёт печатается без цветных заливок: максимум
  жирным, штриховкой, серой шкалой и знаками (для ч/б принтера).
* **Ориентация листа** — вертикально (книжная) или горизонтально (альбомная);
  ориентация применяется и к превью, и к печати (`@page { size: A4 ... }`),
  кнопка печати подписана текущей ориентацией.
* **Компактность** — 4 ступени плотности (шрифт, отступы в ячейках).
* **Оформление** — «Классика», «Полосы», «Строгий», «Акцент».
* **Графики на листе** — полосы по позициям, структура (кольцевая диаграмма),
  продажи по дням; показатель выбирается (выгода / прибыль / выручка /
  количество), количество позиций в графике — Топ-5/8/12 или все.
* **Колонки и блоки листа** — любые колонки (№, кол-во, цены, выручка, суммы,
  прибыль, выгода, маржа) и блоки (шапка, плашки итогов, таблица, строка
  «ИТОГО», расшифровка продаж, артикул, подпись, сноска) включаются галочками.
* **Выравнивание и масштаб** — числа по правому краю/по центру, названия
  слева/по центру; размер таблицы подбирается автоматически по содержимому
  либо задаётся вручную; знак ₽ в ячейках можно отключить.
* **Масштаб превью** — «По ширине» (авто) или 100/85/70/50 %; настройки и
  выбранный масштаб сохраняются в localStorage вместе с отчётом.

Ширины колонок считаются по фактическому содержимому (заголовки + значения +
строка «ИТОГО», замер текста через canvas) и для листа, и для интерактивной
таблицы-редактора — числа и тексты остаются внутри своих ячеек и выровнены,
ничего не «вылезает» и не разъезжается.

### Отчёт для директора (многостраничный)

Компонент `src/components/admin/ProfitReportDirector.tsx`. Каждый блок
печатается с новой страницы A4 (в превью листы идут один за другим):

1. **Сводный лист**: KPI (выручка, прибыль, выгода, продано, «обычно берут»
   в месяц, средний заказ, прогноз количества/выручки/выгоды), сводная
   таблица по всем позициям (цена, себестоимость, конкурент, выручка,
   прибыль, выгода, маржа, динамика, прогноз месяца), структура выгоды,
   прогноз спроса по позициям, рейтинг «где выгода», клиенты с долями и
   выводами по ассортименту.
2. **Отдельный лист на каждую позицию**: KPI позиции, продажи по месяцам
   с линией среднего и штриховкой-прогнозом, кто и сколько обычно берёт
   (объёмы, число заказов, доля, средний заказ, интервал), сравнение цен
   (себестоимость / конкурент / средняя продажа), таблица месяцев с
   прогнозом по среднему и по тренду (метод наименьших квадратов),
   рекомендации (цена, маржа, объём, зависимость от клиента) и все продажи
   периода с отклонением от себестоимости.

Состав отчёта, число позиций (все или первые N) и показатели настраиваются
в панели печати. Расчёты прогноза и рекомендаций — `computeDirectorStats()`
и `computeDirectorSummary()` в том же файле.

## 🧱 Плитки разделов на главной

Главная страница вместо блока «Популярные товары» показывает **плитки разделов**
(фото + название). Клик по плитке мгновенно раскрывает привычное окно каталога
(поиск, список разделов, сетка товаров) — без перехода и перезагрузки: товары
всех плиток приходят вместе со страницей, переключение работает как вкладки.

Настройка — `Админка → Товары и категории → Плитки на главной`:

- **Порядок** — стрелками ↑↓ + «Сохранить порядок».
- **Фото плитки** — загрузка через Cloudinary. Если фото нет, берётся фото
  категории, затем фото первого товара раздела.
- **Правило отбора**: категория каталога · метка/бейдж · популярные ·
  распродажа · весь каталог.
- **Метки товара** (`Карточка товара → Метки товара`): «озон», «вб», «сдэк»,
  «гост»... У одного товара их может быть несколько — он попадёт сразу в
  несколько плиток. Бейдж товара («Хит», «Акция») тоже работает как метка.

Каталог (`/catalog`) не менялся — плитки это только витрина главной.

Перед первым использованием применить миграцию:
`supabase/migration_home_tiles.sql` (добавляет `products.tags` и таблицу
`home_tiles`). До применения миграции главная автоматически собирает плитки из
видимых категорий каталога.

## 🚚 Путевой лист водителя (Доставки / Перевозки)

`Админка → Учёт → Доставки` (или `/deliveries`) — одна перевозка = один путевой лист
на день: водитель, дата и точки маршрута по порядку.

- **Порядок точек настраивается**. Карточки точек перетаскиваются за ручку ⠿ (номер
  точки), либо кнопками ↑/↓/«в начало». Порядок массива `transports.items` и есть
  порядок маршрута — отдельной колонки сортировки не завели, миграция не нужна.
  В созданной перевозке порядок правится в раскрытой карточке и сохраняется кнопкой
  «Сохранить порядок» (`PATCH /api/admin/transports/[id]` → `updateTransport`).
- **Пометки на точке**: «📥 Забор груза», «🚚 Доставка клиенту», «📤 Сдача груза» —
  ставятся на любой точке (и на точке из заказа тоже). Пометка влияет только на бланк:
  списание склада считается по позициям заказа и от пометки не зависит.
- **В бланке пометка дополняется предметом операции** (`stopOperation()`): приём
  макулатуры (ПМ) печатается как «ЗАБОР МАКУЛАТУРЫ», сдача (СМ) — «СДАЧА МАКУЛАТУРЫ»,
  забор поставки (ПО) — «ЗАБОР ТОВАРА», точка из заказа с доставкой — «ДОСТАВКА
  ЗАКАЗА». Свои точки (без документа) остаются с общей пометкой — что там грузят,
  диспетчер пишет в названии. Если у старой точки пометка не сохранена, операция
  берётся по документу (ПМ/ПО — забор, СМ — сдача, заказ — доставка), поэтому
  «Доставка макулатуры» вместо забора в бланк не попадёт.
- **Сколько везём / сколько забираем** — число в строке груза точки: у заказа (ЗК)
  и у поставки (ПО) оно может быть меньше, чем в документе (максимум — остаток).
  Правится и при создании рейса, и в уже созданном (`Сохранить порядок`), и в окне
  «Завершить перевозку» — там видно все числа, которые пойдут на склад, с кнопками
  «Столько» и «Всё». Завершение рейса проводит **ровно эти числа**: по заказу
  списывается со склада только увезенное (`shipped_items`), по поставке на склад
  встаёт только принятое. Недовезли / приняли не всё — документ **не** закрывается:
  заказ остаётся без `completed` и `delivery_released_at`, поставка — без статуса
  «принята» и с пометкой «Заберём сами», поэтому оба снова попадают в список
  доставок с остатком и едут следующим рейсом (в поставке остаток также можно
  добрать кнопкой «Принять остаток»).
- **Своя точка без заказа** — «+ Своя точка»: контрагент, адрес, телефон, контактное
  лицо, время и груз. В груз можно вписать что угодно («макулатура», «поддоны»,
  «ключи в охране»), можно брать позиции из склада через «Из каталога».
- **Быстрые сортировки**: «Сначала забор», «Сначала доставка», «По адресу (А→Я)»,
  «По времени» — внутри группы ручной порядок не меняется.
- **Печать — «Путевой лист (А4)»**: `TransportTripSheet`. Сверху вниз, по порядку,
  карточки точек: крупный номер «N из M» и количество единиц, пометка операции, адрес
  (самый крупный шрифт), телефон, контактное лицо, что делаем на месте, груз списком
  (с «заказано N · не хватает M»), оплата на месте, инструкция (заметка диспетчера +
  общее правило по типу операции), строки «принял/сдал · время · проблемы». Если у точки
  нет телефона — в карточке печатается телефон диспетчера. Внизу: итоги по маршруту,
  подписи (принял/сдал, тара и возврат ТМЦ, выдал, выезд/заезд/пробег).
  Настройки печати (груз списком / одной строкой / без грузов, «максимально компактно»,
  отметки, инструкции, «Авто / гос. номер», «Выдал») запоминаются в localStorage.
- **«Полоски под УПД»** (`TransportPrintSheet`) остались как были — отрывные полоски на
  каждый заказ, в том же порядке точек, что и путевой лист; в шапке полоски теперь
  та же подпись операции («Забор макулатуры», «Забор товара», «Доставка заказа»),
  в том числе у доставок.
- Предпросмотр бланка доступен прямо в модалке создания («Предпросмотр»), до сохранения.

Модель точек и общие хелперы — `src/lib/trip-stops.ts` (одинаковые для редактора,
путевого листа и полосок, чтобы клиентские компоненты не тянули серверный `lib/warehouse.ts`).
Поле `plannedTime` и пометка `tripType` живут в `transports.items` (JSONB) — миграция не нужна.

Стенд для просмотра вёрстки бланка без базы данных — `/trip-sheet-preview`
(модалка перевозок и сами бланки на моковых данных). Страница существует только
в разработке, в production она отдаёт 404. Параметры: `?sheet=1` — сразу открыть
путевой лист, `?admin=1` — показать блок «как это выглядит в админке».

## 🖼 Фото товаров и копирование платежей

- **Копия платежа** (`Учёт → Банк`, кнопка «Копировать» у любого платежа —
  и в «Ожидают оплаты», и в «История (архив)»): открывает форму нового платежа
  с подставленными **контрагентом и суммой**. Дата ставится сегодняшняя,
  комментарий, тип платежа («куда придут деньги») и привязка к документам
  заполняются заново.
- **Библиотека шаблонов фото** (`Товары → Фото-генератор → шаг «Дизайн карточки»`):
  дизайн можно сохранить под именем, применить позже, **скопировать** («Копировать
  шаблон» — создаёт копию и сразу открывает её для доработки) и удалить.
  Шаблоны хранятся в `settings` под ключом `photo_templates` — миграция не нужна.
- **Замена фото**: в карточке товара новая загрузка **заменяет** текущее фото,
  а не добавляет второе. Нужна галерея — снимите галочку «Заменять фото при
  загрузке». В фото-генераторе замена тоже включена по умолчанию.

## 🪟 Модалки: закрытие только Esc и крестиком

Ни одна модалка (админка, форма запроса цены на сайте) **не закрывается кликом по
подложке**. Причина: когда текст в форме выделяют мышью и отпускают кнопку уже за
пределами окна, браузер порождает `click` по подложке — модалка закрывалась, а
введённые данные пропадали.

Закрытие — только крестиком/кнопкой «Отмена» и клавишей **Esc** (хук
`src/hooks/use-escape-close.ts`, `useEscapeClose(onClose, enabled)`; `enabled`
привязывают к состоянию модалки и к `!saving`, чтобы окно не закрывалось во время
сохранения). У новой модалки достаточно не вешать `onClick` на
`.admin-modal-overlay` и вызвать этот хук.

Исключения — не модалки, а всплывающие слои: поповер настроек в «Зарплатах»
(`.whsal-pop-overlay`) и маркетинговые попапы на сайте (`PromotionPopups`)
по-прежнему закрываются кликом мимо.

## 💰 Общий счёт макулатуры и вторая карта «Карта В.М.»

### Общий счёт макулатуры

Наличка и безнал в учёте макулатуры — **по факту один денежный счёт**. Поэтому в
остатках они показываются одной строкой **«Общий счёт макулатуры»**
(`balance.common = cash + bank`), а ниже расшифровка: «Наличка … · Безнал …».
**«Сторонние пополнения» остались отдельной строкой** и в общий счёт не входят.

Данные при этом не склеены: в каждом документе по-прежнему видно, каким счётом
платили (`WP_COMMON_ACCOUNTS`, `wpCommonBalance()` в
`src/lib/wastepaper-account-shared.ts`). Общий счёт показан в трёх местах:
остатки на вкладке «Дни и финансы» (десктоп и мобильный список) и карточка
«Счета макулатуры» на вкладке «Банк».

### Карта В.М. — вторая карта

В банке учёта две карты: **Карта ЮМ** и **Карта В.М.** Это отдельные денежные
счета: на каждую попадают только те деньги, которые переведены именно на неё, у
каждой свой баланс, свой прогноз и своя вкладка.

- Платёж: тип `vm_card` в `bank_payments` (CHECK-ограничения на `type` нет).
- Зарплата: `source = vm_card` в формах, в БД — `source='bank'` + тег
  `[Карта В.М.]` (как у карты ЮМ), см. `salarySourceToDb()`.
- Сдача кассы: поступление и расход помечаются одной из трёх касс — наличные,
  карта ЮМ, карта В.М. (`CashKind`, `cashItemCardAmounts()`,
  `getCashCollectionIncomeBreakdown().vmCard`, `vm_transfer_amount`).
- Балансы: `getBankSummary()` возвращает `vmCardBalance`, `vmExpectedIn/Out`,
  `vmForecast`; итоговый `balance` включает обе карты.
- Закупки: счёт `vm_card` добавлен в `PurchaseAccount`.

Миграция: [`supabase/migration_vm_card.sql`](./supabase/migration_vm_card.sql)
(колонка `vm_transfer_amount` и расширение CHECK для `cash_destination`).

### Настройки банка и печать листа A4

Админка → Настройки → вкладка **«Настройки банка»**: для каждой карты
(ЮМ и В.М.) хранятся владелец (ФИО), номер карты, телефон и банк
(ключи `bank_card_{ym|vm}_{holder|number|phone|bank}`; получатель карты ЮМ
синхронизирован с прежней настройкой сдачи кассы).

Кнопка **«Печать A4»** печатает по листу на карту: крупно номер карты,
получатель в виде «Вадим Маркович П.» (имя и отчество полностью, фамилия
инициалом — `formatCardHolderName()`), телефон и банк. Карты для печати
отмечаются галочками, можно задать число копий
(`src/components/admin/BankCardPrint.tsx`).
