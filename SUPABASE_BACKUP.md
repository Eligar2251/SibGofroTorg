# Supabase как резервная БД для SibGofroTorg

## Можно ли это реализовать?

**Да — частично.** Для этого сайта, где вся логика данных завязана на `firebase-admin/firestore` (`src/lib/firestore-queries.ts`, ~1380 строк, + все API-роуты и админ-страницы), полностью перевести «обе работали» как равноправные БД — это фактически переписать весь слой данных. Это возможно, но требует массовых изменений в каждом файле (`src/app/api/*`, `src/app/[adminPath]/*`, `src/lib/*`).

**Что сделано здесь:**
- Создана полноценная схема `supabase/schema.sql` (только таблицы, без Functions/Buckets).
- Настроены RLS-политики (`ENABLE ROW LEVEL SECURITY`) с защитой:
  - Публичное чтение для категорий, товаров, акций, одобренных отзывов/вопросов, попапов.
  - Админская запись (`admins` таблица) для управления контентом.
  - Пользовательская вставка для заказов, отзывов, вопросов, просмотров, заявок на макулатуру.
- Добавлен клиент `src/lib/supabase.ts` (анон-ключ, без обхода RLS).
- Написаны запросы `src/lib/supabase-queries.ts` с зеркалом основных операций из Firestore.
- Бесплатный тариф Supabase поддерживает всё это (500 МБ БД, 2 ядра, RLS, без Functions/Buckets).

## Как это работает вместе с Firestore

В текущем состоянии **Firestore остаётся основной БД**. Supabase выступает как **резервная/параллельная** структура:
- Вы можете экспортировать данные из Firestore в Supabase (например, через скрипт) для резервного хранения.
- Если нужно использовать Supabase как активный резерв, потребуется дополнительный слой синхронизации или замена вызовов `getAdminDb()` на `supabase` в конкретных модулях.
- Запросы в `supabase-queries.ts` уже готовы для этого — они возвращают те же типы (`FirestoreCategory`, `FirestoreProduct` и т.д.).

## Что нужно для запуска

1. Создайте проект в Supabase (бесплатный тариф).
2. В панели проекта скопируйте:
   - `Project URL` → `NEXT_PUBLIC_SUPABASE_URL`
   - `anon public` → `NEXT_PUBLIC_SUPABASE_ANON_KEY`
3. Добавьте переменные в `.env.local`:
   ```
   NEXT_PUBLIC_SUPABASE_URL=https://xxxx.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJ...
   ```
4. Выполните `supabase/schema.sql` в SQL Editor проекта (или через `supabase db push`, если используете CLI).
5. Создайте хотя бы одну запись в таблице `admins` с вашим `user_id` из `auth.users`, чтобы RLS-политики записи работали.
6. Установите зависимость:
   ```bash
   npm install @supabase/supabase-js
   ```

## Защита без Functions / Buckets

- **Нет Functions**: RLS-политики — это чистый SQL (`CREATE POLICY ... USING (...)`). Никаких Edge Functions или Database Functions не используется.
- **Нет Buckets**: Файлы (изображения) не хранятся в Supabase Storage; они остаются в Cloudinary / Firebase (как в текущем проекте).
- **Защита:** `auth.uid()` проверяет, что запрос идёт от авторизованного пользователя. Админские действия требуют записи в `admins`.

## Ограничения бесплатного тарифа

- 500 МБ базы данных.
- 2 ядра (shared CPU), 2 ГБ RAM.
- Без автоматического масштабирования.
- Для больших каталогов рекомендуется индексация (индексы уже прописаны в `schema.sql`).

## Вывод

**Полностью заменить Firestore на Supabase «чтобы обе работали» без переписывания данных — нельзя в рамках одного файла.** Но инфраструктура для резервной БД с полноценной защитой (RLS) и запросами готова и работает с бесплатным тарифом. Вы можете использовать её как резерв или постепенно мигрировать конкретные разделы, заменяя вызовы в `src/lib/supabase-queries.ts` вместо `firestore-queries.ts` там, где это нужно.
