# Realtime в админ-панели — анализ и карта внедрения

Документ-анализ (без изменений кода). Контекст: БД переехала на **self-hosted Supabase
на VPS Beget**, платная подписка, Realtime-сервис доступен. Задача — понять, где в
админке реалтайм даст реальную пользу.

Кратко:

1. В коде **уже написан** слой реалтайма (`src/lib/use-admin-realtime.ts` + 5 компонентов),
   но физически он **никогда не подключался** — три блокера, каждый из которых
   самостоятельно достаточен, чтобы всё молча уходило в polling-фоллбэк.
2. Даже после починки подключения «в лоб» через `postgres_changes` + anon-ключ работать
   будет только часть таблиц, а для финансовых — работать и **не должно** (утечка).
   Для них нужен другой контур: broadcast из БД + приватный канал.
3. Мест, где реалтайм даёт ощутимый эффект, — около 14. Приоритезированная карта в
   разделе 5.

---

## 1. Что уже есть в коде

| Где | Компонент | Таблицы в подписке | Фоллбэк |
|---|---|---|---|
| Дашборд `/{admin}` | `DashboardRealtime` | `orders`, `wastepaper_requests`, `bank_payments`, `salaries`, `cash_collections`, `customer_deals`, `warehouse_receipts` | polling 30 c |
| Заявки `/{admin}/orders` | `OrdersRealtime` | `orders`, `wastepaper_requests` | polling 20 c |
| Учёт `/{admin}/warehouse` | `WarehouseRealtime` | `customer_deals`, `warehouse_receipts`, `bank_payments`, `products` | polling 20 c |
| Доставки `/{admin}/deliveries` | `DeliveriesRealtime` | `customer_deals` | polling 20 c |
| Отзывы `/{admin}/reviews` | `ReviewsRealtime` | `product_reviews` | polling 30 c |
| Заявки клиентов | `ClientRequestsManager` (хук внутри) | `client_requests` | polling 30 c |

Механика хука: подписка на `postgres_changes` через anon-ключ → на любое событие
`router.refresh()` (полная перерисовка RSC-страницы). Если за 5 секунд канал не поднялся —
включается `setInterval(router.refresh, N)`.

Отдельно живёт мёртвый `OrdersAutoRefresh.tsx` (refresh каждые 15 c) — не импортируется
нигде, кандидат на удаление.

## 2. Почему реалтайма фактически нет (три блокера)

### 2.1. Клиент не знает URL Supabase — самый главный

`src/lib/supabase.ts`:

```ts
export function getSupabaseUrl_pub(): string {
  return process.env.SUPABASE_URL || "";   // ← в браузере всегда ""
}
```

Next.js подставляет в клиентский бандл **только** переменные с префиксом `NEXT_PUBLIC_`
(в `next.config.ts` блока `env` нет). В браузере `process.env.SUPABASE_URL` — `undefined`,
значит в хуке срабатывает ветка

```ts
if (!url || !key) { startPolling(); return; }
```

и WebSocket не создаётся **никогда**. Все шесть мест из таблицы выше сейчас работают
исключительно как polling. Проверяется за 10 секунд: DevTools → Network → WS, при открытой
админке подключений нет.

Лечится добавлением `NEXT_PUBLIC_SUPABASE_URL` в окружение и чтением его в `getSupabaseUrl_pub()`.

### 2.2. CSP не пропустит self-hosted домен

`src/proxy.ts`, `connect-src`:

```
... https://*.supabase.co https://*.supabase.in wss://*.supabase.co wss://*.supabase.in
```

Разрешены только облачные домены Supabase. Ваш self-hosted инстанс на Beget будет на
собственном домене (условно `https://sb.sibgofrotorg.ru`) — браузер заблокирует и REST,
и `wss://`. Нужно добавлять origin из переменной окружения (и `https://`, и `wss://`),
а не хардкодом.

### 2.3. RLS: подписка на большинство таблиц вернёт тишину

`postgres_changes` уважает RLS: событие доходит до клиента, только если у роли из JWT есть
`SELECT` на строку. В `supabase/schema.sql` RLS включён на всех рабочих таблицах, а политик
для `anon` **намеренно нет** (доступ только через `service_role` с сервера).

| Таблица | Политика для anon | Что придёт по подписке |
|---|---|---|
| `orders` | `orders_sel USING (TRUE)` | придёт всё |
| `product_reviews`, `products`, `categories`, `promotions`, `settings` | SELECT true | придёт |
| `customer_deals`, `bank_payments`, `salaries`, `cash_collections`, `warehouse_receipts`, `counterparties`, `employees`, `client_requests`, `transports`, `activity_logs` | политик нет | **ничего** |

То есть даже с починенным подключением дашборд и «Учёт» останутся немыми по деньгам и
сделкам. А выдавать `anon` SELECT на `bank_payments`/`salaries` **нельзя**: anon-ключ
публичный, он лежит в JS-бандле сайта, и любой посетитель выкачает зарплаты через REST.
Это прямо описано в `supabase/migration_rls_public_tables.sql`.

Плюс к тому в публикацию `supabase_realtime` из миграций добавлены только `client_requests`
и `wp_*` — остальные таблицы, даже открытые политикой, событий не порождают, пока не
выполнить `ALTER PUBLICATION supabase_realtime ADD TABLE ...`.

> Побочная находка, к реалтайму не относится, но серьёзная: политика
> `orders_sel USING (TRUE)` означает, что **любой** с anon-ключом уже сейчас может выкачать
> все заявки с именами и телефонами клиентов через `/rest/v1/orders`. Стоит закрыть отдельно.

## 3. Какая архитектура тут уместна

Админка не использует Supabase Auth — у неё своя сессия (`admin-session`, JWT на `jose`,
роли `admin/manager/lawyer/wastepaper`). Значит, «просто подписаться анонимно» для закрытых
данных не подходит. Разумно развести два контура.

### Контур A — `postgres_changes`, публичные/некритичные таблицы

Подходит для того, что и так открыто на чтение: `products` (остатки), `product_reviews`,
`product_questions`, `promotions`, `settings`, `home_tiles`. Дёшево, без дополнительной
инфраструктуры: добавить таблицы в публикацию и подписаться.

### Контур B — Broadcast из БД + приватный канал, для всего рабочего

Для сделок, банка, зарплат, макулатуры, логов:

1. Триггеры на таблицах вызывают `realtime.broadcast_changes()` (или `pg_notify`-подобную
   вставку в `realtime.messages`) в топик вида `admin:warehouse`, `admin:finance`,
   `admin:wastepaper`, `admin:logs`.
2. В payload — **только сигнал**: `{ table, op, id, updated_at, actor }`. Никаких сумм,
   телефонов и ФИО. Даже при утечке канала утекает «в сделке X что-то изменилось».
3. Канал приватный (`private: true`), доступ регулируется RLS-политикой на
   `realtime.messages`.
4. Клиент авторизуется коротким JWT (15–60 мин), который выдаёт новый серверный маршрут
   (условно `/api/admin/realtime-token`) — только владельцу валидной `admin-session`,
   подписанный вашим self-hosted `JWT_SECRET`, с клеймами `role: authenticated` и
   `admin_role: admin|manager|lawyer|wastepaper`. Политика на `realtime.messages` пускает
   в `admin:finance` только `admin/manager/lawyer`, в `admin:wastepaper` — `admin/wastepaper`
   и т. д. Ровно та же матрица прав, что в `src/lib/admin-rbac.ts`.

Плюс: сигнальный payload позволяет обновлять точечно — «пришло событие по сделке 123» →
дозапросить одну сделку своим API, а не перерисовывать всю страницу.

### Контур C — Broadcast/Presence без БД

Чистая передача сообщений между вкладками, без записи в Postgres: «кто сейчас в панели»,
«Иван открыл сделку №123», прогресс импорта, тосты. Ничего не стоит по БД и даёт самые
заметные для людей эффекты (раздел 5, P2).

## 4. Сколько сейчас тратится на опрос (и что вернёт реалтайм)

На каждую открытую вкладку админки:

| Опрос | Период | В час | Что тянет |
|---|---|---|---|
| `ActivityLogs` | **5 с** | 720 запросов | `/api/admin/activity-logs?limit=500` — 500 строк каждые 5 секунд |
| `AdminNotifications` | 30 с | 120 | `/api/admin/notifications` |
| `AdminRequestAlerts` | 30 с | 120 | **тот же** `/api/admin/notifications` — эндпоинт дёргается дважды |
| `/{admin}/warehouse` | 20 с | 180 полных refresh | страница грузит остатки, поступления, сделки, платежи, зарплаты, контрагентов, перевозки, инкассации, планы поставок и закупок + 500 заказов + 200 пользователей |
| `/{admin}/orders`, `/deliveries` | 20 с | по 180 | 500 сделок, 200 перевозок, весь склад |
| Дашборд | 30 с | 120 | агрегаты по всем модулям |

Отдельно про `/api/admin/notifications`: один вызов читает 50 заказов + 50 заявок на
макулатуру + **1000 товаров** + 300 сделок + **2000 платежей** + данные аренды. И так
240 раз в час на вкладку, потому что его опрашивают два колокольчика.

Условные 5 открытых вкладок в офисе — это порядка 6–7 тысяч бесполезных запросов в час,
99% которых возвращают ровно то же самое. Реалтайм убирает не «секунды задержки», а вот эту
постоянную фоновую нагрузку на VPS.

## 5. Карта: куда пристроить реалтайм

### P0 — делать в первую очередь

**1. Новые заявки: колокольчики + `/{admin}/orders`**
Таблицы: `orders`, `wastepaper_requests`, `client_requests`.
Заявка с сайта появляется у менеджера мгновенно (сейчас — до 30 секунд), со звуком и
тостом. Два колокольчика (`AdminNotifications`, `AdminRequestAlerts`) переводятся с опроса
на подписку и перестают дёргать тяжёлый агрегатный эндпоинт. Самый заметный для людей эффект
при наименьших усилиях.

**2. Учёт → Сделки/Заказы (`customer_deals`)**
Несколько менеджеров работают параллельно. Сегодня двое могут одновременно открыть сделку и
затереть правки друг друга, а отгрузку — провести дважды. Реалтайм + пометка «карточку
редактирует Иван» (Presence) закрывают целый класс конфликтов. Список сделок обновляется
без F5.

**3. Склад и сканер (`products`, `warehouse_receipts`, `product_variants`)**
Кладовщик сканирует товар телефоном (`/{admin}/scan`) — остаток на ПК менеджера меняется
сразу. Инвентаризация (`StockRevision`) вдвоём перестаёт быть лотереей: видно, какие позиции
уже пересчитал напарник. Плюс приёмка (`WarehouseReceipts`) — оприходовали на складе, в
кабинете видно.

**4. Банк и касса (`bank_payments`, `cash_collections`, `salaries`)**
Балансы «Расчётный счёт сейчас» / «Касса сейчас» на дашборде и в модуле «Банк» — это ровно
те цифры, ради которых сейчас жмут F5. Инкассация (`CashCollectModal`) двумя людьми
одновременно без синхронизации особенно неприятна.

### P1 — заметная польза

**5. Доставки и перевозки (`transports`, `customer_deals`)**
Водитель отмечает выдачу с телефона → диспетчер видит статус рейса сразу.
Замечание: `DeliveriesRealtime` подписан только на `customer_deals`, а сам модуль работает
с `transports` (12 обращений в `src/lib/warehouse.ts`) — таблицы в подписке не хватает.

**6. Заявки клиентов / CRM (`client_requests`)**
Единственная таблица, уже добавленная в публикацию `supabase_realtime`
(`migration_client_requests.sql`). Готова к подключению, нужна только политика доступа.

**7. Модуль макулатуры (`wp_intakes`, `wp_shipments`, `wp_payments`, `wp_transports`, `wp_counterparties`)**
Все пять таблиц уже в публикации (`migration_wastepaper_account.sql`), но в самом модуле
реалтайма нет вообще. Приёмщик на весовой + бухгалтер за компьютером — классический сценарий
двух устройств на один документ.

**8. Журнал действий (`activity_logs`)**
Append-only лента — идеальный кандидат: одна строка приходит по подписке и дописывается
сверху. Убирает самый агрессивный опрос в системе (5 секунд, 500 строк). Заодно превращается
в живую ленту «кто что делает прямо сейчас».

**9. Аренда (`rent_invoices`, `rent_payments`)**
Частота изменений низкая, но напоминания о просрочках висят на дашборде и в колокольчике —
логично питать их тем же каналом, а не отдельным опросом.

**10. Отзывы и вопросы (`product_reviews`, `product_questions`)**
Уже подписаны и таблицы открыты политиками — заработает сразу после починки подключения.
Стоит добавить `product_questions`: вопрос с сайта требует ответа не меньше отзыва.

### P2 — новые возможности, которых сейчас нет в принципе

**11. Presence: кто в панели**
Аватарки/список «сейчас в админке: Иван (Учёт), Мария (Банк)». Дальше — «Иван редактирует
сделку №123, откроется только на чтение». Для 4 ролей и общей кассы это не украшение, а
защита данных.

**12. Тосты о действиях коллег (Broadcast)**
«Мария провела платёж на 120 000 ₽», «Новая заявка от +7 913…», «Отгрузка по сделке №451
закрыта». Без перезагрузки данных вообще — чистое сообщение в канал.

**13. Прогресс длинных операций**
Массовая загрузка заказов (`BulkDealImporter`), импорт/экспорт Excel, `bulk-create` товаров,
генерация фото (`PhotoTemplateGenerator`, `generate-images`). Сервер шлёт прогресс в канал —
видно «142 из 500», вкладку можно закрыть и вернуться. Сейчас это «висящая» кнопка без
обратной связи.

**14. Сканер как пульт**
Отсканировал коробку на складе телефоном — карточка товара открылась на мониторе у менеджера
(broadcast в персональный канал пользователя). Дешёвая функция, а в связке «склад + офис»
экономит проходы.

### P3 — не трогать / сначала переделать

- **Охрана, график дежурств** (`duty-schedule`): состояние хранится в `localStorage`
  (`useDutySchedule.ts`), в БД его нет. У каждого свой график, синхронизации нет вообще.
  Реалтайму нечего слушать, пока модуль не переедет в Postgres. Само по себе это, кстати,
  более серьёзная проблема, чем отсутствие реалтайма.
- **Настройки, SEO, генератор фото, печатные формы, подбор коробки** — правит один человек
  и редко, реалтайм не нужен.
- **Публичный сайт**: технически можно показывать живые остатки в карточке товара, но это
  трафик от анонимных посетителей на Realtime-сервер VPS. Разумнее ограничиться проверкой
  наличия при оформлении заказа. Единственное осмысленное исключение — «товар закончился,
  пока он лежал у вас в корзине».

## 6. Технические замечания к текущей реализации

Пригодятся, когда дойдёт до внедрения.

1. **`router.refresh()` на каждое событие — слишком грубо.** На `/{admin}/warehouse` одно
   изменение остатка вызывает перезагрузку страницы, которая тянет ~15 запросов, включая
   500 заказов и 200 пользователей. Массовый импорт (200 строк) породит 200 таких refresh
   подряд. Нужен как минимум debounce/коалесcинг (300–500 мс), а лучше точечное обновление
   состояния по сигналу.
2. **Свои же изменения возвращаются эхом.** Пользователь сохранил сделку → сервер обновил
   строку → пришло событие → `router.refresh()` поверх собственного `router.refresh()`.
   Нужен фильтр по `actor` (кто инициировал) в payload.
3. **Фоновые вкладки.** Сейчас polling тикает и в скрытой вкладке. Стоит вешать
   `visibilitychange` и не обновлять невидимое, а при возврате — один раз догонять.
4. **Нет индикатора соединения.** «Данные живые» / «связь потеряна, обновление раз в 30 с» —
   важно, чтобы люди понимали, чему верят на экране, особенно в финансовых модулях.
5. **Имя канала.** `admin-realtime-${tables.join("-")}` — при переходе между страницами
   каналы пересоздаются; для нескольких вкладок разумнее один общий канал на пользователя
   с фильтрацией на клиенте.
6. **Фоллбэк оставить.** Polling как запасной путь — правильное решение, менять не надо;
   только увеличить интервал (60–120 с), когда основной канал жив.
7. **`REPLICA IDENTITY`.** Для получения `old_record` в UPDATE/DELETE (например, чтобы понять,
   что именно изменилось в сделке) таблицам нужен `REPLICA IDENTITY FULL`. Это плата в
   виде объёма WAL — включать точечно.
8. **Мёртвый код**: `OrdersAutoRefresh.tsx` нигде не используется.

## 7. Порядок внедрения

| Этап | Содержание | Результат |
|---|---|---|
| 0 | `NEXT_PUBLIC_SUPABASE_URL` + origin self-hosted в CSP | существующие 6 подписок оживают; отзывы/товары/заявки работают сразу |
| 1 | Публикация + политики для «открытого» контура A | остатки, отзывы, вопросы, заявки — живые |
| 2 | `/api/admin/realtime-token` + RLS на `realtime.messages` + триггеры broadcast | закрытый контур для сделок, банка, макулатуры, логов |
| 3 | Точечные обновления вместо `router.refresh()` в тяжёлых модулях | снимается основная нагрузка на VPS |
| 4 | Presence и тосты | «кто редактирует», «кто в панели», уведомления о действиях |
| 5 | Прогресс длинных операций, сканер-пульт | новые сценарии |

Этапы 0–1 — небольшая правка и одна миграция. Этап 2 — основная работа, но именно он
открывает финансовые модули, ради которых всё и затевается.

# ЧАСТЬ 2. Что реализовано

Ниже — то, что уже сделано в коде (не план, а факт).

## Транспорт: SSE вместо прямой подписки из браузера

Из трёх блокеров раздела 2 два (`NEXT_PUBLIC_SUPABASE_URL` и CSP) вообще исчезли,
потому что браузер больше не ходит в Supabase напрямую:

```
Postgres → Supabase Realtime → [сервер приложения, service_role] → SSE → вкладки админки
                                src/lib/realtime-hub.ts            /api/admin/events
```

- **Один** WebSocket к Supabase на весь сайт, а не один на вкладку.
- Браузер слушает собственный домен (`connect-src 'self'`) — CSP править не нужно.
- Анонимный ключ не участвует: подписку держит `service_role`, поэтому RLS-политики
  для anon не нужны и раздавать их **нельзя** (см. раздел 2.3).
- Доступ к потоку — по существующей `admin-session` cookie; набор таблиц фильтруется
  по роли (`tablesForRole`): юрист слышит только финансы, макулатурщик — только свой модуль.
- Если канал к Supabase не поднялся, сервер честно сообщает об этом первым сообщением,
  и клиент оставляет polling включённым.

Новых переменных окружения не требуется — используются уже имеющиеся
`SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`.

**Перед первым использованием применить миграцию**
`supabase/migration_realtime_admin.sql` — она добавляет таблицы в публикацию

## Гарантии обновления (три контура)

Раньше, если канал к Supabase **подключился, но события не пришли** (таблицы не
добавлены в публикацию `supabase_realtime`, Realtime-сервис не включён,
события потерялись), клиент видел статус `live` и **полностью отключал
polling** — данные обновлялись только после ручного F5. Это и была причина
жалобы «реалтайм не работает, приходится обновлять страницу».

Теперь обновление гарантировано в любом из трёх состояний:

| Состояние | Что делает клиент |
|---|---|
| канал жив и события приходят | `router.refresh()` сразу (коалесcинг 400 мс) |
| канала нет (`connecting`/`offline`) | polling каждые `pollIntervalMs` (20–60 c в модулях) |
| канал жив, но молчит | **страховочный** `router.refresh()`, если за `safetyPollMs` (по умолчанию 60 c) не было ни одного обновления |

Страховочный опрос — не «на всякий случай дёргаем всё»: один тикер на 10 c
проверяет время с последнего обновления (событийного ИЛИ страховочного) и
рендерит максимум раз в минуту. Свои же изменения по событию сбрасывают
счётчик, поэтому при живом канале лишний refresh почти никогда не стреляет.

Дополнительно:

- **watchdog в хубе** (`realtime-hub.ts`): если канал висит в `connecting`
  дольше 20 c — соединение рвётся и переподключается; статусы пишутся в
  консоль сервера строками `[realtime-hub]` (на VPS это способ видеть,
  почему реалтайм мёртв, без захода в браузер);
- **индикатор в углу админки** (зелёная точка «живые данные» / красная
  «обновление по таймеру»): человек видит, что ему верит экран, и понимает,
  почему данные не «летят»;
- **`GET /api/admin/events/status`** — быстрая диагностика для админа:
  `status` (connected/error/idle), `error`, `listeners`, таблицы роли;
- **свежесть данных на сервере** — все write-функции `src/lib/warehouse.ts`
  и `src/lib/supabase-queries.ts` после записи вызывают `revalidateTag` по
  своим тегам кэша (`unstable_cache`, TTL 60–120 c), поэтому любой
  `router.refresh()`/F5 сразу отдаёт данные с учётом последней записи.

## Уведомления о заявках со звуком

`src/components/admin/AdminRequestAlerts.tsx`:

- Заявка с сайта → INSERT в `orders` → событие в SSE → перезагрузка списка →
  звук + всплывающее окно с именем и телефоном клиента.
- **Пропущенные заявки не теряются.** Список уже «прозвонённых» id лежит в
  `localStorage`; всё, чего в нём нет, считается новым. Открыли админку утром —
  сигнал прозвучит за всё, что пришло ночью.
- **Автоплей.** Браузер не даёт играть звук до первого взаимодействия со страницей.
  Если сигнал не смог прозвучать, заявка НЕ помечается услышанной, в интерфейсе
  появляется «Включить звук», и сигнал догоняет после первого клика.
- Звук синтезируется через WebAudio (никаких mp3 в репозитории), отключается кнопкой
  в панели, состояние запоминается.

## Локальная проверка без Supabase (дебаг)

`scripts/mock-realtime.mjs` — мок сервера Supabase Realtime: подняв его и
указав на него `SUPABASE_URL`, можно проверить всю цепочку
«событие → серверный хаб → SSE → браузер» без реального Supabase
(после каждого join мок сам шлёт тестовые изменения `orders` и `salaries`).

```bash
node scripts/mock-realtime.mjs            # мок на :3200
SUPABASE_URL=http://127.0.0.1:3200 SUPABASE_SERVICE_ROLE_KEY=test pnpm dev
# и открыть /api/admin/events с cookie админки:
#   hello → status:connected → change:orders → change:salaries
```
